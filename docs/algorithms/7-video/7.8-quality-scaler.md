# 7.8 QP-based quality scaler

Section 7, *Video quality and processing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Region-of-interest quality -> quality scaler and per-codec QP control

## The issue

The bandwidth estimate alone does not tell the sender whether its resolution is right. Content complexity matters: a talking head at 300 kbps looks fine at 640x360, while a busy scene at the same bitrate falls apart. The encoder reports how hard it is quantizing (QP). A consistently high QP means the picture is blocky and a lower resolution would look better; a consistently low QP means bits are to spare and resolution could rise. QP is noisy from frame to frame, its scale differs per codec, and decisions must not oscillate.

## Design

When the bitrate is too low for the resolution the encoder raises its quantizer (QP) and the picture turns blocky; a smaller resolution at the same bitrate looks better. The scaler averages the QP of encoded frames (exponential filter) and, every `sampling_period`:

```
  avg QP > high threshold, or > 60% frames dropped  -> adapt down
  avg QP < low threshold                             -> adapt up
```

Thresholds are per codec (libwebrtc defaults): VP8 29/95 (0..127), VP9 120/180 and AV1 145/205 (0..255), H.264 24/37 (0..51). After a resolution change the filter is reset so the next decision uses QP measured at the new resolution. Region-of-interest QP (lower QP on faces or text) is an encoder-side refinement on top of these thresholds.

`version = 2` is libwebrtc M157's QualityScaler (#84 step 2), ported from compare/webrtc/reference/modules/video_coding/utility/quality_scaler.cc with its constants: the first check 2 s (`kMeasureMs`) after the first Check() call (libwebrtc starts its task at construction), then every 2 s while `fast_rampup_` (until the first adapt-down) and every 2 s x 2.5 (`kSamplePeriodScaleFactor`) = 5 s after it; 1 s while the previous check saw too few frames. A check needs 60 frames (`kMinFramesNeededToScale`) over a 150-frame window (`5 * 30`), encoded or dropped. It reports high QP when the drop rate over that window is >= 60% (`kFramedropPercentThreshold`, rounded down) or the smoothed QP is > high, and low QP when it is <= low; every report clears the samples. QP is smoothed as QualityScalingExperiment does by default (it is on unless the `WebRTC-Video-QualityScaling` trial says `Disabled`): two rtc::ExpFilter-style filters over the sample times in ms, alpha 0.9995 for the high check and 0.9999 for the low check, read as int, with drops of every reason counted. The experiment's source is not in reference/ (#57); sm_video_compare matches libwebrtc's binary on every quality-scaler row with these values (docs/results/video-webrtc.md).

restrictions a resource asks for and the frame size the source produces.

VideoStreamAdapter is the MAINTAIN_FRAMERATE part of libwebrtc's VideoStreamAdapter, ported from compare/webrtc/reference/call/adaptation/video_stream_adapter.cc and video_source_restrictions.cc (the reference files of #302):

```
  - adapt down (DecreaseResolution): max_pixels_per_frame = 3/5 of the
    current input frame's pixels (GetLowerResolutionThan), target unset;
    refused (kLimitReached) when that is not below the current maximum or
    falls under min_pixels_per_frame (EncoderInfo::ScalingSettings,
    kDefaultMinPixelsPerFrame = 320 x 180);
  - adapt up (IncreaseResolution): target = 5/3 of the input pixels
    (GetHigherResolutionThan), or unrestricted when this undoes the last
    step; max_pixels_per_frame = 12/5 of the target
    (GetIncreasedMaxPixelsWanted); refused when that is not above the
    current maximum;
  - after a step it waits for the input frame size to change before taking
    another in the same direction (awaiting_frame_size_change_).
```

The other degradation preferences (BALANCED's frame-rate steps and BalancedDegradationSettings, MAINTAIN_RESOLUTION) and the per-resource bookkeeping of ResourceAdaptationProcessor are not ported: a camera call uses MAINTAIN_FRAMERATE, and the quality scaler is the only resource wired so far. BitrateConstraint allows every step when the encoder reports no resolution bitrate limits, which the test bench's encoder model does not.

VideoAdapter is libwebrtc's api/video/video_adapter.cc AdaptFrameResolution for one input size and the sink's max/target pixel counts (no output format request, no aspect-ratio crop, no frame-rate limit): FindScale alternates 3/4 and 2/3 (starting with 2/3 when both sides divide by 3) and picks the scale closest to the target that is not above the maximum, then rounds the crop to the scale's denominator times the alignment. VideoStreamEncoder's VideoSourceSinkController passes the restrictions as the sink wants (max_pixel_count, target_pixel_count).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#7-video-quality-and-processing) for the differences from libwebrtc. Per-region QP (ROI) is an encoder-side feature built on top of these thresholds.

```cpp
namespace sm::video {

struct QpThresholds {
  int low = 24;
  int high = 37;
  static QpThresholds ForCodec(const std::string& codec);
};

struct QualityScalerConfig {
  QpThresholds thresholds;
  TimeDelta sampling_period = TimeDelta::Millis(1500);
  int min_frames = 15;
  double smoothing = 0.15;           // EMA weight per frame.
  double max_drop_ratio = 0.6;
  // 2: libwebrtc M157's QualityScaler (see above); the four fields above
  // apply to version 1 only.
  int version = 1;
  EventSink* events = nullptr;
};

class QualityScaler : public MetricsSource {
 public:
  enum class Signal { kNone, kAdaptDown, kAdaptUp };
  explicit QualityScaler(QualityScalerConfig cfg = {}) : cfg_(cfg) {}
  // `now` is the frame's send time (libwebrtc's ReportQp time_sent_us); only
  // version 2 uses it, and without it takes the time of the last Check().
  void OnEncodedFrame(int qp, Timestamp now = Timestamp::MinusInfinity());
  void OnFrameDropped();
  Signal Check(Timestamp now);
  // Call after the resolution changed in response to a signal. Version 2
  // already cleared its samples with the signal, as libwebrtc does, so this
  // does nothing there.
  void OnResolutionChanged();
  double average_qp() const { return avg_qp_; }
  void ExportMetrics(MetricsWriter& w) const override;

  };
  enum class Result { kInsufficientSamples, kNormalQp, kHighQp, kLowQp };
  Signal CheckV2(Timestamp now);
  Result CheckQpV2() const;
  TimeDelta NextCheckDelayV2() const;
  void ClearSamplesV2();

  QualityScalerConfig cfg_;
  double avg_qp_ = 0;
  // Version 2 state.
  static constexpr size_t kDropWindow = 5 * 30;
  std::array<uint8_t, kDropWindow> drops_{};  // 100 per dropped frame, as MovingAverage.
  size_t drop_count_ = 0;                     // Samples since the last clear.
  int drop_sum_ = 0;
  QpSmoother high_{0.9995f}, low_{0.9999f};
  bool fast_rampup_ = true;
  bool prev_observed_enough_ = false;  // CheckQpTask::Result::observed_enough_frames.
  Timestamp next_check_ = Timestamp::MinusInfinity();
  int frames_ = 0, dropped_ = 0;
  Timestamp last_check_ = Timestamp::MinusInfinity();
  uint64_t downs_ = 0, ups_ = 0;
};

}  // namespace sm::video
```

## Verification notes

An expectation was wrong: at 300 kbps, 640x360 already gives QP 33, which is inside the H.264 band, so not going lower is correct. The test now checks that QP returns inside the band. The test bench and `sm_compare` share an encoder model for this module's inputs (`testbench/encoder_model.h`, issue #84 step 1): QP 30 at libwebrtc's per-resolution start rates (720p 1000 kbps, 360p 500 kbps), +6 per halving of the bits per frame, clamped to 0..51, and 10 ms per 720p frame of encode time. Deviation: a model in place of a codec, identical on both stacks, so scaling decisions compare like for like. `version = 2` (issue #84 step 2) is libwebrtc M157's `QualityScaler` (`modules/video_coding/utility/quality_scaler.cc`) with `QualityScalingExperiment`'s default smoothers: 2 s checks until the first adapt-down, then 5 s; 60 frames over a 150-frame window; drop rate >= 60%; smoothed QP > high or <= low. `sm_video_compare` gives the same signals as libwebrtc on all six quality-scaler inputs ([results](../../results/video-webrtc.md)); the unit tests port `quality_scaler_unittest.cc`. Issue #84 step 4 wires version 2 into the send path behind `quality_scaling` (`rtp::VideoSendController`, scenario key `quality_scaling on`, off by default): libwebrtc's `QualityScalerResource` with `MAINTAIN_FRAMERATE`, `VideoStreamAdapter`'s resolution steps (3/5 down, 5/3 up with a 12/5 maximum, the 320x180 minimum, waiting for the frame size to change), `VideoAdapter`'s 3/4-2/3 scale series and `VideoStreamEncoder::DropDueToSize` (up to 4 initial frames dropped as too large for the target, each adapting down), from `call/adaptation/` and `api/video/video_adapter.cc` (reference files of #302). `sm_compare` runs libwebrtc with the same settings (`ScalingSettings(24, 37)`, `MAINTAIN_FRAMERATE`, its own `VideoAdapter` in the source, and `QualityScalingExperiment`'s default string with H.264's 24/37 in the Generic slot, since the encoder model is H.264's QP scale). Not ported: the BALANCED and MAINTAIN_RESOLUTION steps, the per-resource bookkeeping of `ResourceAdaptationProcessor` (one resource so far), the initial-drop reset on a start-bitrate drop (off by default), and the dropped frame kept as `pending_frame_`. `issue_84_quality_scaling_720p_low_rate` and `issue_84_quality_scaling_rate_rise` lock in the behaviour.
