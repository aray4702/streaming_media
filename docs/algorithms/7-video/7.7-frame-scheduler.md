# 7.7 Render timing and late-frame dropping

Section 7, *Video quality and processing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Frames arriving too late to render -> render timing and late-frame dropping

## The issue

Decoded frames become ready at irregular times because of network jitter, frame-size differences and decode time. Showing each frame the moment it is ready makes motion judder. Playback should follow the capture timing, which means deciding a render time per frame. When a frame misses its render time anyway (a delay spike), showing it late only delays the frames behind it. After a stall, a backlog of frames must not be played in slow motion. The renderer must stay smooth while dropping only what cannot be shown in time.

## Design

Decodable frames arrive with a target render time (from timing::VideoTiming: capture time mapped to the local clock plus the playout delay). The scheduler starts decoding each frame `decode_time` before its render time and then:

```
  - renders it if it is on time (or at most `max_late` late);
  - if it is later than that and a newer frame is already waiting, it
    decodes it but skips rendering ("dropped late"), since showing a
    stale frame only delays the newer one;
  - if it is the newest frame it is rendered anyway (better late than a
    freeze).
```

If the queue grows beyond `max_queue` (a burst after a stall), it jumps ahead: everything up to the newest frame is decoded without rendering. Frames must be decoded in order (they reference each other), so skipped frames are still decoded.

A port of the scheduling half of libwebrtc's VideoStreamBufferController (video/video_stream_buffer_controller.cc) and FrameDecodeTiming (video/frame_decode_timing.cc), used by rtp::RtpReceiver under `timing.version = 2` in place of video::FrameScheduler:

```
  - the next decodable frame is scheduled when it reaches the front, with
    its render time from VcmTiming::RenderTime and a latest decode time of
    render_time - estimated decode time - render delay (10 ms), clamped to
    [now, now + the 3 s frame time-out - 1 ms];
  - a frame is fast-forwarded (dropped without decoding) only if it is at
    least 5 ms past that point *and* a later temporal unit is decodable.
    Delta frames each reference the one before them, so only a later
    keyframe can be; a late delta frame with no keyframe behind it is
    decoded and rendered, however late (libwebrtc has no 10 ms late-drop
    rule);
  - on release: VcmTiming::OnDecodableTemporalUnit (jitter estimate,
    minimum delay) and, unless the frame was retransmitted,
    UpdateCurrentDelay; the timing is reset if the render time is more
    than 10 s from now or the target delay is over 10 s;
  - while a keyframe is required (call start) the first keyframe is
    released at once and the frames before it are dropped.
```

The decoder is modelled as ready again as soon as a frame is released. libwebrtc's FrameHasBadRenderTiming/TargetVideoDelayIsTooLarge (video/frame_helpers.cc) are not in compare/webrtc/reference/; the 10 s bounds follow their kMaxVideoDelay (noted on #57).

A port of libwebrtc M157's IncomingVideoStream and VideoRenderFrames (video/render/incoming_video_stream.{h,cc}, video/render/video_render_frames.{h,cc}), which VideoReceiveStream2 puts between the decoder and the renderer when `enable_prerenderer_smoothing` is on, its default (video/video_receive_stream2.cc:400).

Each decoded frame carries its render time. The queue:

```
  - drops a frame whose render time is more than 500 ms in the past, but only
    when other frames are waiting (kOldRenderTimestampMS);
  - drops a frame more than 10 s in the future (kFutureRenderTimestampMS);
  - drops a frame whose render time is earlier than the last one queued
    ("scheduled out of order");
  - releases frames `render_delay` before their render time; when several are
    due at once, only the newest is rendered and the older ones are dropped.
```

A frame added to an empty queue is dequeued at once (IncomingVideoStream::OnFrame calls Dequeue when AddFrame returns 1); while frames wait, the next dequeue runs at the front frame's release time (PostDelayedHighPrecisionTask). Times are in whole ms, as libwebrtc's clock reads.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#7-video-quality-and-processing) for the differences from libwebrtc.

## Verification notes

Exposed the 4.6 jitter-offset defect (render-interval jitter 7.9 ms before the fix, 1.1 ms after). Timing v2 ([fix record](../../fixes/24-timing-v2.md), partial for #24): `timing::FrameReleaseController` releases frames as libwebrtc's VideoStreamBufferController and FrameDecodeTiming do. A late frame is skipped only when a later temporal unit (here a keyframe) is decodable, so the 10 ms late-drop rule is gone: with every v2 switch on, `issue_53_cwnd_pushback`'s link renders 28.8-29.2 fps on seeds 1-10 (timing v1 16.0-20.8, libwebrtc 27-28); `issue_24_timing_v2_render_fps` locks it in. Issue #437 (partial): `video::RenderFrames` ports libwebrtc's pre-render queue (video/render/incoming_video_stream.cc, video_render_frames.cc), behind `render_smoothing` (on by default since #437's flip, as libwebrtc). With it on, `very_low_capacity` seeds 1-10 render 466 -> 421 frames and freeze 25.3 -> 24.6 times (libwebrtc 369 and 21.3); `issue_437_render_smoothing_very_low_capacity` locks it in ([fix record](../../fixes/437-render-smoothing.md)). Issue #583: with timing v2 the receiver's frame buffer holds at most 800 frames as libwebrtc's FrameBuffer (video_stream_buffer_controller.cc:46, frame_buffer.cc:84-106): in a full buffer a delta frame is refused and a keyframe clears it, a frame at or below the last decoded id is refused unless it is a keyframe with a newer RTP timestamp, which clears it; unit tests `RtpReceiver.AFullFrameBuffer...` and `RtpReceiver.AfterAPacketBufferReset...`.
