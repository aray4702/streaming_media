# 7.7 Render timing and late-frame dropping

Section 7, *Video quality and processing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Frames arriving too late to render -> render timing and late-frame dropping

## The issue

Decoded frames become ready at irregular times because of network jitter, frame-size differences and decode time. Showing each frame the moment it is ready makes motion judder. Playback should follow the capture timing, which means deciding a render time per frame. When a frame misses its render time anyway (a delay spike), showing it late only delays the frames behind it. After a stall, a backlog of frames must not be played in slow motion. The renderer must stay smooth while dropping only what cannot be shown in time.

## Design

Decodable frames arrive with a target render time (from timing::VideoTiming: capture time mapped to the local clock plus the playout delay). The scheduler starts decoding each frame `decode_time` before its render time and then:

```
  - renders it if it is on time (or at most `max_late` late);
  - if it is later than that and a newer frame is already waiting, it
    decodes it but skips rendering ("dropped late"), since showing a
    stale frame only delays the newer one;
  - if it is the newest frame it is rendered anyway (better late than a
    freeze).
```

If the queue grows beyond `max_queue` (a burst after a stall), it jumps ahead: everything up to the newest frame is decoded without rendering. Frames must be decoded in order (they reference each other), so skipped frames are still decoded.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#7-video-quality-and-processing) for the differences from libwebrtc. 

## Implementation skeleton

Files: [include/sm/video/frame_scheduler.h](../../../include/sm/video/frame_scheduler.h), [src/video/frame_scheduler.cc](../../../src/video/frame_scheduler.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::video {

struct ScheduledFrame {
  int64_t id = 0;
  Timestamp render_time;
};

struct FrameAction {
  int64_t id = 0;
  bool render = false;
  Timestamp render_time;
  TimeDelta lateness;  // Positive = late.
};

struct FrameSchedulerConfig {
  TimeDelta decode_time = TimeDelta::Millis(5);
  TimeDelta max_late = TimeDelta::Millis(10);
  size_t max_queue = 30;
  EventSink* events = nullptr;
};

struct FrameSchedulerStats {
  uint64_t frames_in = 0, decoded = 0, rendered = 0, dropped_late = 0, fast_forwards = 0;
  Histogram lateness_ms;  // Rendered frames only (negative clamped to 0).
};

class FrameScheduler : public MetricsSource {
 public:
  explicit FrameScheduler(FrameSchedulerConfig cfg = {}) : cfg_(cfg) {}
  void Insert(const ScheduledFrame& f);
  std::vector<FrameAction> Process(Timestamp now);
  // Next time Process() has work to do.
  Timestamp NextWakeup() const;
  size_t queued() const { return queue_.size(); }
  const FrameSchedulerStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::video
```

## Metrics and observability

Every class implements `MetricsSource::ExportMetrics`, so it can be registered in a `MetricsRegistry` and exported as JSON or Prometheus text. Histograms expand to `.count/.mean/.p50/.p95/.p99/.max`.

| Metric | Type |
|---|---|
| `frames_in` | counter |
| `decoded` | counter |
| `rendered` | counter |
| `dropped_late` | counter |
| `fast_forwards` | counter |
| `queued` | gauge |
| `lateness_ms` | histogram |

Structured events (`EventSink`, `module/name`): `frame_scheduler/fast_forward`, `frame_scheduler/drop_late`.

## Test methods

**Unit tests** (deterministic, no network):

- `FrameScheduler`: `RendersOnTimeDropsLateWhenNewerWaiting`, `FastForwardOnHugeBacklog`

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_FrameScheduler`: `SmoothPlayoutOverJitteryNetwork`

30 fps over 15 ms jitter: VideoJitterEstimator + VideoTiming give render times and the scheduler presents frames. Render-interval jitter is compared with rendering on arrival.
