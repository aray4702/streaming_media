# 7.1 Freeze detection

Section 7, *Video quality and processing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Lost frame (decode impossible) -> freeze the last frame until recovery (measured as freezes)

## The issue

When a frame cannot be decoded, the receiver keeps showing the last good picture, and the user sees frozen video. Freezes are the most noticeable video quality problem, yet average frame-rate statistics hide them: one 2-second freeze in a minute barely moves the average fps. Operators need a consistent definition of what counts as a freeze (versus normal frame-rate variation or a deliberate pause), plus counts and durations, to detect and debug bad calls.

## Design

A freeze is an inter-frame interval of at least

```
    max(3 * avg_frame_duration, avg_frame_duration + 150 ms)
```

as libwebrtc's VideoQualityObserver::OnRenderedFrame counts it (video/video_quality_observer2.cc): intervals are in whole ms, the average is over the last 30 intervals including the current one and earlier freezes, rounded down to whole ms, and the test starts once 5 intervals are in it. Gaps of 5 s or more are pauses (libwebrtc's OnStreamInactive, e.g. the sender stopped the track), counted separately and kept out of the average. Also tracks the sum of squared frame durations, which gives the harmonic frame rate that weights long frames (what a viewer perceives) more than the arithmetic fps does.

When decoding is impossible the receiver keeps showing the last frame; this detector quantifies how often and how long that happens.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#7-video-quality-and-processing) for the differences from libwebrtc. Keyframe requests that end freezes are in 3.5.

## Implementation skeleton

Files: [include/sm/video/freeze_detector.h](../../../include/sm/video/freeze_detector.h), [src/video/freeze_detector.cc](../../../src/video/freeze_detector.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::video {

struct FreezeStats {
  uint64_t frames_rendered = 0;
  uint64_t freeze_count = 0;
  double total_freezes_ms = 0;
  uint64_t pause_count = 0;
  double total_pauses_ms = 0;
  double total_frames_duration_ms = 0;
  double sum_squared_frame_durations_s2 = 0;
  // Longest freeze, kept as a plain value because `freeze_ms` records nothing
  // when metrics are compiled out (SM_ENABLE_METRICS=0).
  double longest_freeze_ms = 0;
  Histogram freeze_ms;
};

class FreezeDetector : public MetricsSource {
 public:
  explicit FreezeDetector(EventSink* events = nullptr) : events_(events) {}
  void OnFrameRendered(Timestamp now);
  // Frames per second weighted by duration (WebRTC "harmonic" fps).
  double HarmonicFps() const;
  const FreezeStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::video
```

## Verification notes

A unit-test expectation was wrong about the harmonic frame rate: irregular 38/38/23 ms intervals give 28.97 fps, not 30.3, which is the point of the metric. #268 ported libwebrtc's freeze rule (`video/video_quality_observer2.cc`, `OnRenderedFrame`): the current interval enters the 30-interval average before the test, freezes stay in it, the average is rounded down to whole ms and the test starts at 5 intervals. `sm_video_compare` now gives libwebrtc's counts on every freeze input (9 vs 9 freezes at 180-230 ms gaps, 7 vs 7 at 3 fps, 57 vs 57 on random gaps), and `FreezeDetector.*` pins them ([fix record](../../fixes/268-freeze-rule-as-libwebrtc.md)).
