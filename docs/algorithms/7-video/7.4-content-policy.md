# 7.4 Content hints and screen-content variable frame rate

Section 7, *Video quality and processing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Screen sharing (text must stay sharp) -> content hint, screen-content coding tools, variable framerate
- Talking head vs. motion -> content-type-aware rate control

## The issue

Not all video is the same. For a camera feed, smooth motion matters most, so under constraint the frame rate should be kept. For a shared document or code, legible text matters most: halving the resolution or raising the quantizer makes text unreadable, while a lower frame rate is barely noticed. Screen content is also static most of the time. Encoding 30 identical frames per second wastes CPU and bandwidth. The encoder pipeline needs to know what kind of content it has, adapt in the right direction, and skip frames where nothing changed, while still sending a changed frame immediately.

## Design

The track's content hint (WebRTC MediaStreamTrack.contentHint) selects how to trade quality under constraint, as libwebrtc's GetDegradationPreference (webrtc_video_engine.cc:2032-2064):

```
  motion  (camera, sports)       keep frame rate, drop resolution
  detail  (slides, documents)    keep resolution, drop frame rate
  text    (code, spreadsheets)   keep resolution, drop frame rate
  none                           screencast keeps resolution, camera
                                 keeps frame rate
```

The hint picks only the degradation preference: libwebrtc derives no QP ceiling, frame-rate floor or cap from it (#877). Screen content additionally uses variable frame rate: FrameChangeDetector hashes 16x16 luma blocks and reports which changed; unchanged frames are not encoded at all (a static slide costs nothing), with a keep-alive frame every `max_idle` so the receiver knows the stream is alive.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#7-video-quality-and-processing) for the differences from libwebrtc. Screen-content coding tools (AV1 palette/intra-BC, HEVC SCC) are encoder features; the policy does not set them.

## Implementation skeleton

Files: [include/sm/video/content_policy.h](../../../include/sm/video/content_policy.h), [src/video/content_policy.cc](../../../src/video/content_policy.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::video {

enum class ContentHint { kNone, kMotion, kDetail, kText };
enum class Degradation { kMaintainFramerate, kMaintainResolution, kBalanced };

struct ContentSettings {
  Degradation degradation = Degradation::kMaintainFramerate;  // libwebrtc's camera default.
};

ContentSettings SettingsFor(ContentHint hint, bool is_screencast);

struct ChangeResult {
  bool changed = false;
  int dirty_blocks = 0;
  double changed_fraction = 0;
};

class FrameChangeDetector : public MetricsSource {
 public:
  explicit FrameChangeDetector(TimeDelta max_idle = TimeDelta::Seconds(1), int block = 16)
      : max_idle_(max_idle), block_(block) {}
  ChangeResult Analyze(const I420Frame& f);
  // Encode decision for variable-frame-rate screen content.
  bool ShouldEncode(const I420Frame& f, Timestamp now);
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::video
```

## Verification notes

No defects found. Issue #581: with no hint, camera video maps to maintain-framerate (the `ContentSettings` default too), as libwebrtc's `GetDegradationPreference` (`media/engine/webrtc_video_engine.cc:2032-2064`; BALANCED only with the `WebRTC-Video-BalancedDegradation` trial, off); it was balanced. Issue #877 (Owner decision): `SettingsFor` and `ContentSettings` carry only the degradation preference; the QP ceilings (40 detail, 32 text), frame-rate floors (15, 2, 1), the screencast frame-rate cap and the variable-frame-rate and screen-tools flags are removed, as libwebrtc derives none of them from the hint. Nothing in the call read them, so no test bench metric moves.
