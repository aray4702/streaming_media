# 7.4 Content hints and screen-content variable frame rate

Section 7, *Video quality and processing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Screen sharing (text must stay sharp) -> content hint, screen-content coding tools, variable framerate
- Talking head vs. motion -> content-type-aware rate control

## The issue

Not all video is the same. For a camera feed, smooth motion matters most, so under constraint the frame rate should be kept. For a shared document or code, legible text matters most: halving the resolution or raising the quantizer makes text unreadable, while a lower frame rate is barely noticed. Screen content is also static most of the time. Encoding 30 identical frames per second wastes CPU and bandwidth. The encoder pipeline needs to know what kind of content it has, adapt in the right direction, and skip frames where nothing changed, while still sending a changed frame immediately.

## Design

The track's content hint (WebRTC MediaStreamTrack.contentHint) selects how to trade quality under constraint:

```
  motion  (camera, sports)       keep frame rate, drop resolution
  detail  (slides, documents)    keep resolution, drop frame rate
  text    (code, spreadsheets)   keep resolution, low QP ceiling, allow
                                 very low frame rates
```

Screen content additionally uses variable frame rate: the capturer delivers a frame only when the screen changes, and FrameCadenceAdapter's zero-hertz mode (frame_cadence_adapter.h, as libwebrtc) repeats the last one while the screen is static (#878).

libwebrtc M157's FrameCadenceAdapter (video/frame_cadence_adapter.cc in compare/webrtc/reference/, issue #878), which replaces the block-hash FrameChangeDetector.

A screen capturer delivers a frame only when the screen changes (a "zero-hertz" source: min fps 0). The adapter sits between the source and the encoder:

```
  - Passthrough mode (camera, and any source that is not zero-hertz):
    every frame goes to the encoder at once, and the input frame rate is a
    RateStatistics over 2970 ms (kFrameRateAveragingWindowSizeMs).
  - Zero-hertz mode, on when the encoder is configured for screen content
    (SetZeroHertzModeEnabled, from VideoStreamEncoder for kScreen) and the
    source's constraints are min fps 0 and max fps > 0
    (IsZeroHertzScreenshareEnabled). Each frame is delayed by one frame
    period (1 / max fps). When no newer frame has arrived, the last frame
    is repeated (an empty update) every frame period until every layer's
    quality has converged (quality_convergence.h), then every
    kZeroHertzIdleRepeatRatePeriod (1000 ms). A new frame cancels the
    repeats; a keyframe request resets convergence and cuts an idle
    repeat short (ProcessKeyFrameRequest). From creation, and again after
    the source discards a frame, the adapter asks the source for a refresh
    frame after 3 frame periods (kOnDiscardedFrameRefreshFramePeriod) and
    then every frame period until a frame arrives. A restricted max frame
    rate (UpdateVideoSourceRestrictions) lengthens the short repeats.
```

The library reads no clock and runs no task queue: the caller passes `now`, calls Process(now) at NextProcessTime(), before any other call at that `now` and again after it, and receives the frames to encode and the refresh-frame requests in order. The delayed tasks run in the order libwebrtc's queue would run them (due time, then post order). Frames are opaque handles; the caller keeps the pixels. Differences from libwebrtc:

```
  - Encoding takes no time on the caller's clock and frames are handled on
    the caller's thread, so `queue_overload` (frames waiting on the encoder
    queue while an encode overran a frame period) is never set.
  - The VSync (metronome) mode is not ported: libwebrtc uses it only when
    the call is given an encode metronome; without one it uses passthrough.
```

libwebrtc M157's QualityConvergenceMonitor and QualityConvergenceController (video/quality_convergence_monitor.cc, video/quality_convergence_controller.cc in compare/webrtc/reference/, issue #878).

VideoStreamEncoder feeds every encoded frame's QP into the controller (video_stream_encoder.cc:2316-2325) and passes the answer to the frame cadence adapter (frame_cadence_adapter.h): once every layer is at target quality, zero-hertz mode slows its repeats of a static frame from the frame rate to one per second.

A layer is at target quality when (QualityConvergenceMonitor::AddSample):

```
  0. the QP is at or below the static threshold (VP8 15, VP9 32, AV1 60, or
     the encoder's min QP if higher; -1, never, for H.264, H.265 and
     generic), or
  1. dynamic detection is on (VP8, VP9, AV1) and, over refresh frames only,
     the mean QP of the older samples (up to 6) is at or below
     static + 0.06 * max QP (127 VP8, 255 VP9/AV1) and at or below the mean
     of the 6 most recent samples. A non-refresh frame clears the window.
```

The field-trial overrides (WebRTC-QCM-Static-*, WebRTC-QCM-Dynamic-*) are not ported; their defaults are.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#7-video-quality-and-processing) for the differences from libwebrtc. Screen-content coding tools (AV1 palette/intra-BC, HEVC SCC) are encoder features; the policy only flags that they should be enabled.

## Verification notes

No defects found. Issue #581: with no hint, camera video maps to maintain-framerate (the `ContentSettings` default too), as libwebrtc's `GetDegradationPreference` (`media/engine/webrtc_video_engine.cc:2032-2064`; BALANCED only with the `WebRTC-Video-BalancedDegradation` trial, off); it was balanced. The QP ceilings and frame-rate floors stay with #566. Issue #878: the block-hash `FrameChangeDetector` (which skipped unchanged frames and sent a 1/s keep-alive) is replaced by a port of libwebrtc's `FrameCadenceAdapter` (`video/frame_cadence_adapter.cc`: passthrough and `ZeroHertzAdapterMode`) and `QualityConvergenceController`/`Monitor` (`video/quality_convergence_*.cc`), with their constants: one frame period of delay, short repeats until quality converges, idle repeats every 1000 ms, refresh-frame requests after 3 periods. Not ported: `queue_overload` (no encoder queue here) and the VSync metronome mode (only with an encode metronome).
