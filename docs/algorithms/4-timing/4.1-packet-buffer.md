# 4.1 Packet buffer: reordering, de-duplication, frame assembly

Section 4, *Jitter, reordering and timing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Out-of-order packets -> sequence-number reordering in the packet buffer
- Duplicate packets -> dedup by sequence number

## The issue

UDP gives no ordering or uniqueness guarantee. Packets of one frame can arrive out of order (per-packet load balancing, Wi-Fi retransmissions, multi-path), duplicated (link-layer retries, mirroring) or interleaved with packets of other frames. A depacketizer that assumes in-order delivery will build corrupt frames or drop good ones. Sequence numbers are 16 bits and wrap every 65 536 packets (a few minutes of video), so "older" and "newer" must be decided on a circle, not by plain comparison.

## Design

Packets are stored by unwrapped sequence number in a bounded window. After each insert the buffer walks forward from the packet as libwebrtc's `PacketBuffer::FindFrames` does (packet_buffer.cc): through packets that are continuous (a frame start, or the next packet of the same RTP timestamp after a continuous one), stopping at a missing packet or one already handed out, and a continuous packet with the marker bit completes a frame: the run of consecutive sequence numbers with its RTP timestamp. (A frame may open with several start packets, e.g. H.264 parameter sets before the IDR slice: it starts at the first of the contiguous packets that share its timestamp, as libwebrtc's `PacketBuffer::FindFrames` walks back for H.264 without a generic descriptor, packet_buffer.cc. A start whose predecessor of the same frame is missing opens the frame there, as libwebrtc does; issue #847. The walk back does not stop at a marker bit, so two frames with one RTP timestamp go out as one, as in libwebrtc; issue #899.) Complete frames are returned immediately (possibly out of order; the frame scheduler orders them by decodability). A copy of a packet still in the buffer and packets older than the window are rejected and counted. A packet leaves the buffer when its frame is handed out, so a copy that arrives after that is taken again until `ClearTo`, as libwebrtc's empty slot takes it (`InsertPacket`'s duplicate check compares only a buffered packet's sequence number): a copy of a one-packet frame is assembled a second time, and the frame buffer drops the repeat (`FrameBuffer::InsertFrame`); issue #899. `drop_copies_after_assembly` keeps the old filter for a receiver that has no frame buffer behind the packet buffer (`timing v1`).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#4-jitter-and-timing) for the differences from libwebrtc. Frame boundaries come from the packetizer's start flag and the RTP marker bit; frames may complete out of order and are ordered later by decodability (3.5) and the frame scheduler (7.7). The buffer is sized as libwebrtc's PacketBuffer (issue #76 group 6; the fixed-window v1 was deleted in #167): 512 slots doubling to 2048 when another unassembled packet maps to a slot, a clear plus a keyframe request when it is full at 2048, and a restart when a packet is 1024 behind the lowest sequence number. Packets leave at frame assembly, and the receiver also calls ClearTo(last sequence number) when a frame leaves the scheduler (issue #101): it drops the packets up to it and ignores older ones; padding is kept only within a quarter of the buffer behind an insert. `missing_packets` (on in a session's H.264 video streams, as libwebrtc, issue #453; on by default in a bare PacketBufferConfig too since #580, which a caller turns off for another codec): libwebrtc's H.264 rule in FindFrames and UpdateMissingPackets (packet_buffer.cc): the sequence numbers not yet received below the newest one (at most 1000 behind it) are kept, a complete frame without an IDR slice is held while one of them is at or before its first packet, a released frame forgets the holes up to its last packet, padding fills a hole, ClearTo forgets the holes below it, and a packet that arrives later releases the held frames it makes contiguous (FindFrames' walk forward). Frame start (issue #847): a frame opens at the first of the contiguous packets that share its timestamp, if that one is a start, even when an earlier packet of the frame is missing, as libwebrtc's H.264 walk back in FindFrames (an IDR slice whose parameter-set packet is lost is handed out alone, as a keyframe). libwebrtc M157 uses `h26x_packet_buffer.cc` for H.264 only under a field trial that is off by default.

## Implementation skeleton

Files: [include/sm/timing/packet_buffer.h](../../../include/sm/timing/packet_buffer.h), [src/timing/packet_buffer.cc](../../../src/timing/packet_buffer.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::timing {

enum class InsertResult { kInserted, kDuplicate, kTooOld, kBufferCleared };

struct AssembledFrame {
  int64_t first_seq = 0;  // Unwrapped.
  int64_t last_seq = 0;
  uint32_t timestamp = 0;
  std::vector<RtpPacket> packets;
  Timestamp last_arrival;
  size_t size_bytes() const;
};

struct PacketBufferConfig {
  size_t window = 2048;  // Packets of history kept for reordering and dedup.
  // libwebrtc's `video_coding::PacketBuffer` sizing (packet_buffer.cc, #76):
  // the buffer starts at `start_size` slots and doubles up to `max_size` when
  // a slot is taken by another sequence number; when it is full at `max_size`
  // it is cleared and the caller asks for a keyframe (`kBufferCleared`); a
  // packet `max_size / 2` or more behind the lowest sequence number seen
  // restarts the buffer.
  size_t start_size = 512;
  size_t max_size = 2048;
  // libwebrtc's `missing_packets_` rule for H.264 without a generic
  // descriptor (packet_buffer.cc FindFrames, UpdateMissingPackets): the buffer
  // keeps the sequence numbers not yet received below the newest one (at most
  // 1000 behind it), and a complete frame without an IDR slice is held while
  // one of them is at or before its first packet. A keyframe is released, and
  // a released frame forgets the holes up to its last packet. A packet that
  // arrives later releases the held frames it makes contiguous, as FindFrames'
  // walk forward does. On by default, as libwebrtc applies it to every H.264
  // frame (issues #453, #580). The buffer does not know the codec: turn it off
  // for another codec, as rtp::Session does for streams that are not H.264.
  bool missing_packets = true;
  // Reject a copy of a packet whose frame was already handed out, as a
  // duplicate. Off by default, as in libwebrtc, whose slot is empty after
  // assembly (issue #899). A deviation for `timing v1` only, whose receive
  // path has no frame buffer to drop a frame assembled twice: RtpReceiver
  // turns it on there.
  bool drop_copies_after_assembly = false;
  EventSink* events = nullptr;
};

struct PacketBufferStats {
  uint64_t inserted = 0;
  uint64_t duplicates = 0;       // A copy of a packet still in the buffer (or, with drop_copies_after_assembly, already handed out).
  uint64_t reinserted = 0;       // A copy of a packet already handed out in a frame, taken again (its slot is empty).
  uint64_t too_old = 0;
  uint64_t cleared = 0;          // The buffer was full at max_size and was cleared.
  uint64_t padding = 0;          // Padding-only packets that held a sequence number.
  uint64_t reordered = 0;        // Arrived after a higher sequence number.
  uint64_t frames_assembled = 0;
  uint64_t frames_held = 0;      // missing_packets: complete delta frames held behind a hole (each time).
  Histogram reorder_distance;    // Packets the late packet was behind.
};

class PacketBuffer : public MetricsSource {
 public:
  explicit PacketBuffer(PacketBufferConfig cfg = {});
  // frame_start: the depacketizer's `is_first_packet_in_frame` (e.g. VP8 S
  // bit; H.264: a parameter set, AUD, SEI, or a slice or FU-A start with
  // first_mb_in_slice 0); the end is the RTP marker bit.
  //
  // `idr`: the packet carries an IDR slice (or its first FU-A fragment), so a
  // frame with it is an H.264 keyframe for the `missing_packets` rule.
  InsertResult Insert(RtpPacket p, bool frame_start, Timestamp now, bool idr = false);
  // A padding-only packet occupied `seq`: it is received, there is nothing
  // to assemble, and it must not look like a hole (or a duplicate later).
  void NotePadding(uint16_t seq);
  // The sequence number just before `first_seq` that is not a padding-only
  // packet, i.e. the last packet of the preceding frame if it was received.
  int64_t PrecedingMediaSeq(int64_t first_seq) const;
  // `PacketBuffer::ClearTo`: the frame ending at `seq` was decoded, so
  // every packet up to and including it is dropped, the lowest sequence number
  // moves past it, and a packet behind it that arrives later is ignored
  // (`kTooOld`) rather than treated as a backward jump.
  void ClearTo(int64_t seq);
  // `PacketBuffer::Clear`: drops every packet and the sequence-number history
  // of the window (the unwrapper keeps its state), as on a full buffer and as
  // RtpVideoStreamReceiver2 does when it re-anchors after a sequence-number
  // discontinuity.
  void Clear();
  std::vector<AssembledFrame> PopCompleteFrames();
  size_t capacity() const { return size_; }
  size_t buffered_packets() const { return packets_.size(); }
  const PacketBufferStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

  };
  bool PotentialNewFrame(int64_t seq) const;
  void FindFrames(int64_t seq);
  bool AssembleFrame(int64_t start, int64_t last);
  void UpdateMissingPackets(int64_t seq);
  void Trim();
  bool SlotTaken(int64_t seq) const;

  PacketBufferConfig cfg_;
  SeqNumUnwrapper<uint16_t> unwrapper_;
  std::map<int64_t, Entry> packets_;
  // Padding-only sequence numbers within the window, for PrecedingMediaSeq.
  std::set<int64_t> padding_;
  // PacketBuffer::received_padding_: the padding FindFrames skips. A found
  // frame forgets it from where the walk started through its last packet, so
  // it is kept apart from `padding_`, which stands in for the reference
  // finder's own padding record.
  std::set<int64_t> received_padding_;
  std::set<int64_t> done_;  // Sequence numbers already delivered in frames (or padding).
  std::set<int64_t> missing_;  // missing_packets: not received, below newest_inserted_.
  int64_t newest_inserted_ = INT64_MIN;
  int64_t highest_ = INT64_MIN;
  size_t size_ = 0;                      // Current slot count.
  bool cleared_to_first_seq_ = false;    // ClearTo moved first_seq_; older packets are ignored.
  int64_t first_seq_ = INT64_MIN;        // Lowest sequence number seen since the last clear.
  std::vector<AssembledFrame> ready_;
  PacketBufferStats stats_;
};

}  // namespace sm::timing
```

## Test methods

**Unit tests** (deterministic, no network):

- `PacketBuffer`: `AssemblesInOrderFrame`, `ReorderedPacketsCompleteFrame`, `DuplicatesAndTooOldRejected`, `FramesAcrossSequenceWrap`, `MissingStartBlocksFrame`

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_PacketBuffer`: `ReorderedDuplicatedStreamAssemblesEveryFrameOnce`

1 500 frames (every third one packet, the others six) over a link with 8 ms Gaussian jitter (heavy reordering) and 3% duplication, with sequence numbers crossing the 16-bit wrap, decoded in order 60 ms after they complete with ClearTo on each decode. Every frame must reach the frame buffer with its packets in order and be decoded exactly once; a copy of a one-packet frame that lands after assembly is assembled again and dropped by the frame buffer's rule, as in libwebrtc (issue #899).

## Verification notes

No defects found. Issue #453: with `sps_pps_tracker on` and `h264_missing_packets on`, `high_jitter` seeds 1-10 keyframe requests 1.8 -> 1.2, the same as libwebrtc on 10 of 10 seeds. Made the session default for H.264 by the #453 flip (see docs/design/libwebrtc-parity.md). Issue #847: the H.264 assembly rules compared with packet_buffer.cc and h26x_packet_buffer.cc; the wait for a missing packet before an IDR start (`may_continue_frame`) removed as libwebrtc has none (unit tests `PacketBuffer.IdrStartOpensTheFrameWhenItsParameterSetPacketIsMissing` and `RtpReceiver.AKeyframeWhoseParameterSetPacketIsLostIsDeliveredFromItsIdr`); suite unchanged. Issue #899: FindFrames' walk forward ported (PotentialNewFrame continuity, received_padding_, stops at a packet already handed out and at a held frame) and the marker-bit stop removed from the walk back (unit tests `PacketBuffer.TwoFramesWithOneTimestampGoOutAsOne`, `PacketBuffer.ForwardWalkStopsWherePaddingIsNoLongerRemembered`); suite unchanged on seed 1. Issue #899 (window ruling, option (a)): a copy of a packet is a duplicate only while the packet is buffered, as InsertPacket's `buffer_[index]->seq_num() == seq_num`; after its frame is handed out the slot is empty and a copy is taken again (`reinserted`) until ClearTo, so a one-packet frame is assembled twice and the frame buffer drops the repeat (FrameBuffer::InsertFrame, already inserted); the receiver counts `frames_received` after the frame buffer takes a frame, as ReceiveStatisticsProxy::OnCompleteFrame (unit tests `PacketBuffer.CopyOfAOnePacketFrameAfterAssemblyIsAssembledAgain`, `PacketBuffer.CopyOfAPacketOfAnAssembledFrameStaysUntilClearTo`, `RtpReceiver.ACopyAfterAssemblyIsAssembledAgainAndTheFrameBufferDropsIt`; e2e `E2E_PacketBuffer.ReorderedDuplicatedStreamDecodesEveryFrameOnce`); suite bit-identical on seed 1. Deviation of the non-default path: `timing v1` has no frame buffer, so its receiver sets `drop_copies_after_assembly` and keeps rejecting such a copy, so a frame is never rendered twice (`RtpReceiver.TimingV1DropsACopyAfterAssemblyInThePacketBuffer`).
