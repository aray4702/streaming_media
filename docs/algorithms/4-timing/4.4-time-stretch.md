# 4.4 Time stretching (WSOLA accelerate / preemptive expand)

Section 4, *Jitter, reordering and timing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Variable packet arrival (audio) -> time-stretching: accelerate, preemptive expand
- Clock drift between sender and receiver -> NetEq stretching

## The issue

When the target playout delay changes, the audio already buffered must be played faster or slower to reach the new level. After a network stall, for example, half a second of packets arrives at once. Simply dropping or repeating whole frames causes audible clicks and stutters. Resampling plays everything faster or slower and shifts the pitch (chipmunk voices) for as long as the correction lasts.

Speech can instead be shortened or lengthened by whole pitch periods, which listeners do not notice, as long as the cut points line up with the waveform's periodicity and the signal is actually periodic there. Without this, a jitter buffer that grew during a spike stays large for the rest of the call.

## Design

preemptive expand).

Accelerate removes one pitch period L from a block of at least 30 ms by crossfading segment A = x[s, s+L) into B = x[s+L, s+2L); preemptive expand inserts one period by crossfading B back into A. Because voiced speech is nearly periodic with period L, the edit is inaudible. Stretching is only applied when the two segments are well correlated, or when the block is near-silent (any lag works then).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#4-jitter-and-timing) for the differences from libwebrtc. Accelerate removes one pitch period by cross-fading segment A into B; preemptive expand inserts one. Both are refused on unvoiced, non-silent audio (correlation < 0.75), where they would be audible. This was the v1 jitter buffer's DSP; the jitter buffer uses NetEq's (NetEqTimeStretch, see 4.5), and since #817 removed version 1 `TimeStretcher` has no caller in the library.

## Implementation skeleton

Files: [include/sm/timing/time_stretch.h](../../../include/sm/timing/time_stretch.h), [src/timing/time_stretch.cc](../../../src/timing/time_stretch.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::timing {

struct TimeStretchConfig {
  int sample_rate = 16000;
  float correlation_threshold = 0.75f;
  float silence_dbfs = -55.0f;
  int min_period_hz = 400;  // Shortest period (highest pitch) considered.
  int max_period_hz = 70;   // Longest period considered (must fit in 30 ms / 2).
};

struct TimeStretchStats {
  uint64_t accelerate_ok = 0;
  uint64_t accelerate_rejected = 0;
  uint64_t expand_ok = 0;
  uint64_t expand_rejected = 0;
  uint64_t samples_removed = 0;
  uint64_t samples_inserted = 0;
};

class TimeStretcher : public MetricsSource {
 public:
  explicit TimeStretcher(TimeStretchConfig cfg = {});
  // Minimum input length in samples (30 ms).
  size_t min_input() const { return static_cast<size_t>(cfg_.sample_rate * 3 / 100); }
  // Writes the stretched signal to `out` and returns the number of samples
  // removed (accelerate) or inserted (expand); 0 means the input was copied
  // unchanged.
  size_t Accelerate(std::span<const float> in, std::vector<float>& out);
  // `old_samples` at the start of `in` were played already and stay as they
  // are: the period is inserted after them (PreemptiveExpand's
  // old_data_length in NetEq).
  size_t PreemptiveExpand(std::span<const float> in, std::vector<float>& out, size_t old_samples = 0);
  const TimeStretchStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::timing
```

## Test methods

**Unit tests** (deterministic, no network):

- `TimeStretch`: `AccelerateRemovesWholePeriods`, `ExpandInsertsWholePeriods`, `RejectsNoiseAcceptsSilence`, `TooShortInputIsCopied`

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_TimeStretch`: `LatencyRecoversAfterStall`

Audio over a quiet network that stalls for 600 ms and then delivers the backlog at once. With stretching the buffer must return to its target; without it the extra 600 ms of latency stays for the rest of the call.

## Verification notes

Defect found in integration: the jitter buffer only decoded audio until it had 10 ms ready, but WSOLA needs 30 ms, so stretching never ran and latency stayed at 600 ms after a stall. Fixed by decoding ahead only when a stretch is wanted (AudioJitterBuffer::MaybeStretch); recovery now takes ~0.5 s.
