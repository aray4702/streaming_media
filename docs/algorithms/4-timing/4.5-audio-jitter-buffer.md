# 4.5 Adaptive audio jitter buffer (NetEq-lite)

Section 4, *Jitter, reordering and timing*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Variable packet arrival (audio) -> NetEq adaptive jitter buffer with time-stretching

## The issue

The audio device pulls exactly 10 ms of samples every 10 ms, at a rate the network does not control, while packets arrive late, early, out of order, duplicated or not at all. Something has to bridge the two clocks: always produce sound on time, play every packet that arrives in time, conceal the ones that do not, and keep the delay as small as the network allows.

That requires several cooperating decisions on every 10 ms pull: normal playout, concealment when the next packet is missing, merging back when it arrives, speeding up when too much is buffered, and slowing down when too little is. A naive FIFO either underruns on every jitter spike or accumulates latency forever.

## Design

Packets (decoded PCM) are inserted on arrival; the audio device pulls a fixed block (10 ms) at a time. On each pull the buffer chooses one operation:

```
  normal            next packet is present and the buffer level is on target
  accelerate        level well above target: drop one pitch period (WSOLA)
  preemptive expand level below target: add one pitch period (WSOLA)
  expand            next packet missing: synthesize audio with PLC
  merge             packet arrives after an expand: crossfade back in
```

The target delay comes from DelayManager (95th percentile of relative arrival delay), so the buffer tracks the network's jitter instead of using a fixed size. With `version = 2` (the test bench's `neteq v2`, issue #62) it comes from NetEqDelayManager, libwebrtc M157's NetEq DelayManager and its packet-arrival history, instead, and the operation is chosen as NetEq's DecisionLogic and NetEqImpl::GetDecision do (NetEqDecisionLogic): playout starts with the first packet; accelerate when the playout delay of the arrival history reaches the target plus its largest arrival delay plus 20 ms, preemptive expand below the target, at most one of them every 5 ticks; decoding is postponed after an expand while the buffer holds less than half the target; and an expand ends in a merge once it has covered the gap to the next packet.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#4-jitter-and-timing) for the differences from libwebrtc. Decoded PCM is inserted (decode-on-insert); a decoder interface that decodes at pull time (to use Opus FEC from the next packet) is a natural extension. Statistics use WebRTC getStats names. NetEq v2 (issue #62, `neteq v2`; default v1) chooses the operation as libwebrtc M157's modules/audio_coding/neteq/decision_logic.cc and NetEqImpl::GetDecision/GetAudioInternal (neteq_impl.cc) do, in `NetEqDecisionLogic` (timing/neteq_delay.h): playout starts with the first packet (new codec: a normal decode, no wait for the target); with the expected packet available and the last mode not an expand, fast accelerate at 4x and accelerate at the arrival history's playout delay >= target + its largest arrival delay + 20 ms, preemptive expand below the target, the last two at most once per kMinTimescaleInterval (5 ticks after a successful stretch, 6 after a reset); decoding is postponed while the buffer (span plus the newest packet's waiting time) is under 50 % of the target and the expand is muted below 0.5; a future packet is merged once the expand has covered the gap or the buffer is above target + 50 ms, otherwise the expand goes on; a missing packet with a later one buffered starts an expand after normal playout. The extraction rules are NetEq's: nothing is decoded while 10 ms is ready, except for merge and the stretches; accelerate needs 30 ms decoded (else normal, decoding 20 ms first); preemptive expand decodes up to 20 ms and borrows the rest of its 30 ms from the samples just played, inserting the period after them. BufferLevelFilter (buffer_level_filter.cc, Q8, factor 251-254 by target) is ported and exported as `filtered_buffer_level_samples`; M157 uses it for no decision. Differences that remain: the stretch DSP is 4.4's (correlation 0.75, segment at the block start), not accelerate.cc/preemptive_expand.cc (0.9, 15 ms); the expand is 3.4's PLC, so the mute factor is its fade (full level for 10 ms, linear to 0 over 50 ms) rather than Expand's signal-dependent mute_slope, and it conceals exactly the missing part of 10 ms instead of Expand's pitch-length chunks; Expand's 5/8 ms overlap is not kept back; fast accelerate is a plain accelerate, as NetEq::Config::enable_fast_accelerate defaults to false (api/neteq/neteq.h, missing from compare/webrtc/reference/, #57).

## Implementation skeleton

Files: [include/sm/timing/audio_jitter_buffer.h](../../../include/sm/timing/audio_jitter_buffer.h), [src/timing/audio_jitter_buffer.cc](../../../src/timing/audio_jitter_buffer.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::timing {

enum class AudioOperation { kSilence, kNormal, kAccelerate, kPreemptiveExpand, kExpand, kMerge };
const char* ToString(AudioOperation op);

struct AudioJitterBufferConfig {
  int sample_rate = 16000;  // RTP clock rate is assumed equal.
  int packet_ms = 20;
  size_t max_packets = 100;
  bool time_stretch = true;
  DelayManagerConfig delay;
  int version = 1;  // 2: the target delay and the operations as libwebrtc's NetEq.
  NetEqDelayConfig neteq_delay;
  EventSink* events = nullptr;
};

// Field names follow WebRTC getStats() (RTCInboundRtpStreamStats).
struct AudioJitterBufferStats {
  uint64_t packets_received = 0;
  uint64_t packets_discarded_late = 0;
  uint64_t packets_duplicate = 0;
  uint64_t packets_lost = 0;                 // Skipped after concealment.
  uint64_t buffer_flushes = 0;
  uint64_t total_samples_received = 0;       // Samples output.
  uint64_t concealed_samples = 0;
  uint64_t concealment_events = 0;
  uint64_t inserted_samples_for_deceleration = 0;
  uint64_t removed_samples_for_acceleration = 0;
  uint64_t ops[6] = {0, 0, 0, 0, 0, 0};      // Indexed by AudioOperation.
  Histogram jitter_buffer_delay_ms;          // Per decoded packet.
};

class AudioJitterBuffer : public MetricsSource {
 public:
  explicit AudioJitterBuffer(AudioJitterBufferConfig cfg = {});

  void InsertPacket(uint32_t rtp_ts, std::vector<float> pcm, Timestamp arrival);
  // Fills `out` (typically 10 ms) and reports the operation performed.
  AudioOperation GetAudio(std::span<float> out, Timestamp now);

  int TargetDelayMs() const;
  double CurrentLevelMs() const;
  // Extra minimum delay, e.g. requested by audio/video synchronization.
  void SetMinimumDelayMs(int ms) {
    min_delay_ms_ = ms;
    neteq_delay_.SetMinimumDelay(ms);
  }
  const AudioJitterBufferStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

  };
  std::map<int64_t, Packet> queue_;
  std::vector<float> sync_;          // Decoded samples waiting for playout.
  int64_t next_ts_ = 0;              // RTP time of the first sample after sync_.
  bool started_ = false;
  bool expanding_ = false;
  int64_t expanded_samples_ = 0;
  double filtered_level_ms_ = 0;
  int min_delay_ms_ = 0;
  AudioJitterBufferStats stats_;
  std::vector<float> scratch_;
  std::vector<float> played_;  // The last 30 ms played out (version 2), for borrowing.
};

}  // namespace sm::timing
```

## Verification notes

See 4.4 for the decode-ahead defect. A first comparison test was wrong: a fixed 20 ms buffer without acceleration does not conceal late packets, it waits for them, so its latency ratchets up (to 4x its target). The test now checks concealment against the loss rate and delay against both fixed buffers. NetEq v2 operations (issue #62): libwebrtc's decision_logic and buffer_level_filter unit tests pass (CNG cases excluded, no CNG here). With `neteq v2` on the whole suite (seeds 1-3), the audio gaps against libwebrtc's 10-seed means go from 112 to 94 (38 closed, 20 opened). `audio_only_lossy` jitter buffer delay p95 60 -> 72 ms and mouth-to-ear 133 -> 145 ms (libwebrtc 81 and 147); `issue_62_neteq_v2_audio_only_lossy` locks it in.
