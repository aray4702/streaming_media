# 3.1 NACK + RTX retransmission

Section 3, *Packet loss*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Lost video packets -> NACK + RTX: selective retransmission on a separate SSRC

## The issue

Video is split into many RTP packets per frame (a 720p keyframe can be 50-100 packets), and a frame can only be decoded when every one of its packets has arrived. On a link with 1-5% random loss, a frame of 8 packets is incomplete 8-34% of the time, so without repair the picture freezes or breaks up constantly. The sender still has the packet, so the cheapest repair is to ask for exactly the missing sequence numbers and resend them.

Doing this naively causes new problems. Asking as soon as a gap appears produces spurious requests when packets are only reordered. Asking again before the retransmission could have arrived doubles the traffic. Retransmitting on the original SSRC corrupts the receiver's loss and jitter statistics. Retrying forever keeps requesting packets that are already too old to be played. The design has to bound retries by RTT and age, put retransmissions on a separate RTX stream, and give up (and ask for a keyframe) when repair is hopeless.

## Design

Detects sequence-number gaps, schedules retransmission requests with RTT-based retry spacing, retires requests that exceed their retry budget, and asks for a keyframe when the missing list can no longer be repaired.

(RFC 4588), where the original sequence number (OSN) is prepended to the payload and the packet is sent on a separate SSRC and payload type.

(RFC 4585 6.3.1), FIR (RFC 5104 4.3.1), loss notification (LNTF, the libwebrtc "goog-lntf" application-layer feedback), and compound RTCP packets (RFC 3550 6.1). Layouts follow libwebrtc's rtcp_packet/ nack, pli, fir and loss_notification so that libwebrtc parses what this library sends. Pure functions: no clock, no state.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#3-packet-loss) for the differences from libwebrtc. Retry spacing is max(RTT x factor, 20 ms) so a request is not repeated before its answer could arrive; the sender also refuses to resend the same packet twice within one RTT, which protects against duplicate NACKs. Overflow handling drops gaps older than the next keyframe instead of the whole list, so a burst does not force an unnecessary keyframe. The request is the standard generic NACK (RFC 4585 6.2.1, PID+BLP items) from loss/rtcp_feedback.h, byte-compatible with libwebrtc's rtcp_packet::Nack (interop check in compare/webrtc/rtcp_interop.cc). RTX history version 2 (`rtx v2`, issue #76 group 2) is libwebrtc's RtpPacketHistory: a packet enters when the pacer sends it, stays max(3 x RTT, 1 s) and is culled after three times that (or when 600 are held and the oldest is past the retention, at most 9600), leaves when transport feedback acknowledges it, and a request is ignored while a resend is queued or within one RTT of the last send. With `rtx v2` and no FEC the RTP sequence number is assigned when the pacer releases the packet (`RtpSender::AssignSequenceNumber`, as `PacketRouter` / `AssignSequenceNumber` do), so a packet a keyframe flush discards leaves no gap (issues #127, #154, [fix record](../../fixes/154-sequence-at-pacer-release.md)). Remaining differences: no early resend of packets that transport-wide feedback reports lost (RtpVideoSender::OnPacketFeedbackVector), and retransmitted-flush settings are off as in the libwebrtc default. With `pacer v2` the history also gives payload padding (`GetPayloadPaddingPacket` in `PaddingMode::kRecentLargePacket`: the most recent large payload, kept after it has left the history), see docs/fixes/120-rtx-payload-padding.md. Version 2 of the NackTracker retries on libwebrtc's 20 ms process tick.

```cpp
struct NackConfig {
  // 1 = the library's original policy. 2 = libwebrtc's NackRequester: giving up
  // after kMaxNackRetries (100) asks for no keyframe, and a full list is
  // cleared and asks for one (issue #23). Default 1 until the final PR.
  int version = 1;

  TimeDelta min_retry_interval = TimeDelta::Millis(20);
```

```cpp
  size_t history_capacity = 1024;              // Packets (power of two not required).
  TimeDelta max_age = TimeDelta::Seconds(2);   // Do not resend older packets.
```

```cpp
namespace sm::loss {

// RTCP packet types used by the library.
inline constexpr uint8_t kRtcpSr = 200;
inline constexpr uint8_t kRtcpRr = 201;
inline constexpr uint8_t kRtcpSdes = 202;
inline constexpr uint8_t kRtcpBye = 203;
inline constexpr uint8_t kRtcpRtpfb = 205;  // Transport-layer feedback (NACK, transport-cc).
inline constexpr uint8_t kRtcpPsfb = 206;   // Payload-specific feedback (PLI, FIR, LNTF, REMB).

// Generic NACK: lost RTP sequence numbers of one media SSRC.
struct Nack {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
  // In the order they were requested. Serialization packs each run of numbers
  // within 16 of the item's first number into one PID+BLP item.
  std::vector<uint16_t> seqs;
};

// Picture loss indication: the decoder lost reference pictures.
struct Pli {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
};

// Full intra request: one entry per requested SSRC. `seq_nr` increases by one
// for each new request and lets the sender ignore retransmitted requests.
struct FirEntry {
  uint32_t ssrc = 0;
  uint8_t seq_nr = 0;
};
struct Fir {
  uint32_t sender_ssrc = 0;
  std::vector<FirEntry> entries;
};

// Loss notification: tells the sender how far the receiver has decoded and
// received, so it can decide whether a keyframe is needed. Sequence numbers
// are those of the frames' generic sequence (16 bits, wrapping).
struct LossNotification {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
  uint16_t last_decoded = 0;
  uint16_t last_received = 0;  // Within 32767 after last_decoded (wrapping).
  // True when every frame that has been received since last_decoded can be
  // decoded once the missing ones arrive (no keyframe needed yet).
  bool decodability_flag = false;
};

// At most this many 32-bit words of NACK items fit one RTCP packet; further
// sequence numbers are dropped by SerializeNack (the session splits earlier).
inline constexpr size_t kMaxNackItems = 65535 - 3;

// Each Serialize returns an empty vector when the message cannot be encoded
// (a NACK with no sequence numbers, a FIR with no entries, a loss notification
// whose last_received is not within 32767 after last_decoded).
std::vector<uint8_t> SerializeNack(const Nack& n);
std::vector<uint8_t> SerializePli(const Pli& p);
std::vector<uint8_t> SerializeFir(const Fir& f);
std::vector<uint8_t> SerializeLossNotification(const LossNotification& l);

// Each Parse takes exactly one RTCP packet (header included) and returns
// nullopt for a wrong packet type or FMT, a bad version, a length that does
// not match the data, or an empty / truncated payload.
std::optional<Nack> ParseNack(std::span<const uint8_t> data);
std::optional<Pli> ParsePli(std::span<const uint8_t> data);
std::optional<Fir> ParseFir(std::span<const uint8_t> data);
std::optional<LossNotification> ParseLossNotification(std::span<const uint8_t> data);

// --- Compound RTCP -------------------------------------------------------------

enum class RtcpType {
  kSenderReport,
  kReceiverReport,
  kNack,
  kTransportCc,
  kPli,
  kFir,
  kLossNotification,
  kRemb,
  kSdes,
  kBye,
  kOther,  // Valid RTCP header, type the library does not interpret.
};

// One packet inside a compound RTCP datagram. `data` includes the header.
struct RtcpPacketView {
  uint8_t packet_type = 0;
  uint8_t fmt = 0;  // The count / FMT field of the first byte.
  RtcpType type = RtcpType::kOther;
  std::span<const uint8_t> data;
};

// Splits a compound RTCP datagram into its packets, validating each header
// (version 2, length inside the datagram, padding only on the last packet).
// Returns nullopt for an empty datagram, a bad header or trailing bytes.
std::optional<std::vector<RtcpPacketView>> SplitCompoundRtcp(std::span<const uint8_t> data);

// Concatenates packets into a compound datagram. As libwebrtc does, the first
// packet must be an SR or an RR (use an RR with no blocks if there is nothing
// to report), and only the last packet may carry the padding bit (RFC 3550
// 6.1); otherwise returns an empty vector. Reduced-size RTCP
// (RFC 5506) is sent without this wrapper.
std::vector<uint8_t> BuildCompoundRtcp(std::span<const std::vector<uint8_t>> packets);

}  // namespace sm::loss
```

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_NackRtx`: `RecoversRandomLossWithinDeadline`, `TooLateAtHighRtt`

30 fps video (8 x 1000 B packets per frame) over a link with 5% random loss in both directions and 40 ms one-way delay. The receiver's NackTracker sends NACKs over the lossy reverse link, the RtxSender answers with RTX packets. A packet counts as on time if it is available within a 250 ms playout budget. A second run at 150 ms one-way delay shows retransmissions arriving too late.
