# 3.5 Keyframe requests (PLI/FIR) and loss notification

Section 3, *Packet loss*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Lost or undecodable video frame -> PLI / FIR keyframe request; LNTF (loss notification)
- Lost frame (decode impossible) -> keyframe request; freeze the last frame until recovery

## The issue

Video frames depend on earlier frames: a P-frame only stores the difference from its reference. If a frame is lost for good, every later frame that depends on it, directly or indirectly, is undecodable until the next keyframe. Most encoders send keyframes rarely or only on request, so the picture freezes indefinitely, or a decoder that decodes anyway shows smeared, corrupted video.

The receiver must ask for a keyframe (PLI, or FIR when joining a stream), but timing is delicate. Asking at the first gap wastes a large keyframe when NACK would have repaired the packet a few milliseconds later. Asking too late lengthens the freeze. Asking repeatedly while the keyframe is in flight causes a request storm of oversized frames that congests the link further.

## Design

notification (LNTF), driven by frame-level decodability.

The receiver tracks which frames are decodable from their references. A frame whose references are missing waits for NACK to repair them for up to `repair_window` (scaled by RTT); after that, or immediately on a decoder error, a PLI is sent. Requests are throttled so a slow keyframe does not trigger a request storm, and retried if no keyframe arrives in time. LNTF reports the first undecodable frame right away so a sender that supports it can react before the PLI.

The repair window (max(200 ms, 2 x RTT)) gives NACK a chance before a keyframe is requested; requests are throttled to max(100 ms, 1.5 x RTT) and retried after twice that.

## Implementation skeleton

Files: [include/sm/loss/keyframe_request.h](../../../include/sm/loss/keyframe_request.h), [src/loss/keyframe_request.cc](../../../src/loss/keyframe_request.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::loss {

struct FrameInfo {
  int64_t frame_id = 0;      // Monotonic (unwrapped) frame id.
  bool keyframe = false;
  std::vector<int64_t> references;  // Frame ids this frame depends on.
};

enum class FeedbackType { kPli, kFir, kLntf };

struct FeedbackMessage {
  FeedbackType type;
  uint8_t fir_seq = 0;            // FIR command sequence number.
  int64_t last_decodable = -1;    // LNTF fields.
  int64_t last_received = -1;
};

struct KeyframeRequestConfig {
  TimeDelta repair_window = TimeDelta::Millis(200);  // Wait for NACK repair.
  double repair_rtt_factor = 2.0;                    // window = max(w, rtt*f).
  TimeDelta min_request_interval = TimeDelta::Millis(100);
  double request_rtt_factor = 1.5;                   // Throttle = max(min, rtt*f).
  bool send_lntf = true;
  size_t max_tracked_frames = 512;
  EventSink* events = nullptr;
};

struct KeyframeRequestStats {
  uint64_t frames_received = 0;
  uint64_t frames_decodable = 0;
  uint64_t frames_dropped = 0;      // Undecodable, discarded at the next keyframe.
  uint64_t pli_sent = 0;
  uint64_t fir_sent = 0;
  uint64_t lntf_sent = 0;
  uint64_t throttled = 0;
  Histogram time_to_keyframe_ms;    // First request -> keyframe received.
};

class KeyframeRequester : public MetricsSource {
 public:
  explicit KeyframeRequester(KeyframeRequestConfig cfg = {});

  // A complete frame (all packets present) was assembled.
  void OnFrame(const FrameInfo& f, Timestamp now);
  // Packets of a frame are permanently lost (NACK gave up).
  void OnFrameLost(int64_t frame_id, Timestamp now);
  void OnDecoderError(Timestamp now);
  // New receiver or stream switch: needs a FIR (full intra request).
  void OnStreamStart(Timestamp now);
  void UpdateRtt(TimeDelta rtt) { rtt_ = rtt; }

  // Feedback to send now.
  std::vector<FeedbackMessage> Process(Timestamp now);
  // Frames that became decodable, in order. Safe to pass to the decoder.
  std::vector<int64_t> TakeDecodableFrames();

  bool waiting_for_keyframe() const { return request_pending_; }
  const KeyframeRequestStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::loss
```

## Metrics and observability

Every class implements `MetricsSource::ExportMetrics`, so it can be registered in a `MetricsRegistry` and exported as JSON or Prometheus text. Histograms expand to `.count/.mean/.p50/.p95/.p99/.max`.

| Metric | Type |
|---|---|

| `frames_decodable` | counter |

| `fir_sent` | counter |
| `lntf_sent` | counter |
| `throttled` | counter |
| `waiting_frames` | gauge |
| `waiting_for_keyframe` | gauge |

Structured events (`EventSink`, `module/name`): `keyframe/received`, `keyframe/frame_lost`, `keyframe/decoder_error`, `keyframe/stream_start`, `keyframe/<reason>`.

## Test methods

**Unit tests** (deterministic, no network):

- `KeyframeRequest`: `InOrderFramesAreDecodable`, `LateReferenceUnblocksWithoutPli`, `PliAfterRepairWindowThenThrottled`, `DecoderErrorAndStreamStart`

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_Keyframe`: `RecoversFromUnrepairableLoss`

30 s of 30 fps video with an IPPP reference chain and 2% unrecoverable frame loss (after NACK). The sender answers each PLI with a keyframe. Measures the decodable-frame ratio, the longest freeze and the number of PLIs (no request storms).

## Verification notes

Pass threshold derived analytically: each unrecoverable loss costs repair window + RTT + keyframe transit, about 10 frames, so 2% loss bounds decodability near 80%. Without keyframe requests only ~3% of frames decode.
