# 3.5 Keyframe requests (PLI/FIR) and loss notification

Section 3, *Packet loss*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Lost or undecodable video frame -> PLI / FIR keyframe request; LNTF (loss notification)
- Lost frame (decode impossible) -> keyframe request; freeze the last frame until recovery

## The issue

Video frames depend on earlier frames: a P-frame only stores the difference from its reference. If a frame is lost for good, every later frame that depends on it, directly or indirectly, is undecodable until the next keyframe. Most encoders send keyframes rarely or only on request, so the picture freezes indefinitely, or a decoder that decodes anyway shows smeared, corrupted video.

The receiver must ask for a keyframe (PLI, or FIR when joining a stream), but timing is delicate. Asking at the first gap wastes a large keyframe when NACK would have repaired the packet a few milliseconds later. Asking too late lengthens the freeze. Asking repeatedly while the keyframe is in flight causes a request storm of oversized frames that congests the link further.

## Design

notification (LNTF), driven by frame-level decodability.

The receiver tracks which frames are decodable from their references, and asks for a keyframe on libwebrtc's RtpVideoStreamReceiver2 triggers (issue #23): the first assembled frame is not a keyframe, a decoder error, the triggers other modules report (OnExternalRequest: the NACK list or the packet buffer overflowed) and the decode time-out. A frame whose references are missing is repaired by NACK. LNTF reports the first undecodable frame right away so a sender that supports it can react before the PLI.

(RFC 4585 6.3.1), FIR (RFC 5104 4.3.1), loss notification (LNTF, the libwebrtc "goog-lntf" application-layer feedback), and compound RTCP packets (RFC 3550 6.1). Layouts follow libwebrtc's rtcp_packet/ nack, pli, fir and loss_notification so that libwebrtc parses what this library sends. Pure functions: no clock, no state.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#3-packet-loss) for the differences from libwebrtc. The receiver asks on libwebrtc's RtpVideoStreamReceiver2 triggers (issue #23): the first assembled frame is not a keyframe, a decoder error, a NACK list or packet buffer overflow, and the decode time-out (200 ms before the first frame, 3 s after; not while a keyframe is arriving or the stream is idle). A keyframe is arriving while a packet came within 200 ms whose depacketized frame type is key (every FU-A fragment of an IDR slice, an SPS or IDR NAL unit) or that has the last keyframe's RTP timestamp, counting packets received as sent only (RtpVideoStreamReceiver2::UpdatePacketReceiveTimestamps, issue #335). A blocked frame is left to NACK: there is no repair window, retry timer or receiver throttle (the v1 policy that had them was deleted in #167). Wire formats (loss/rtcp_feedback.h): PLI (RFC 4585 6.3.1), FIR (RFC 5104 4.3.1, with its own request sequence number), loss notification (LNTF, libwebrtc's goog-lntf application-layer feedback) and compound RTCP with the report first; each is checked against libwebrtc's parsers in compare/webrtc/rtcp_interop.cc. On the sender, the test bench runs libwebrtc's EncoderRtcpFeedback::OnReceivedIntraFrameRequest (video/encoder_rtcp_feedback.cc): a PLI or FIR within kMinKeyframeSendIntervalMs (300 ms) of the last one passed to the encoder is ignored (rtp::VideoSendController, `min_keyframe_request_interval`; issue #151). The outage monitor's own request is not filtered.

```cpp
namespace sm::loss {

struct FrameInfo {
  int64_t frame_id = 0;      // Monotonic (unwrapped) frame id.
  bool keyframe = false;
  std::vector<int64_t> references;  // Frame ids this frame depends on.
};

enum class FeedbackType { kPli, kFir, kLntf };

struct FeedbackMessage {
  FeedbackType type;
  uint8_t fir_seq = 0;            // FIR command sequence number.
  int64_t last_decodable = -1;    // LNTF fields.
  int64_t last_received = -1;
};

struct KeyframeRequestConfig {
  // libwebrtc has no repair window, no retry timer and no receiver-side
  // throttle (the v1 policy, deleted by #167).
  bool send_lntf = true;
  // The decode time-out, from compare/webrtc/reference/video/
  // (added by PR #95):
  //  - video_receive_stream2.h kMaxWaitForKeyFrame 200 ms and kMaxWaitForFrame
  //    3 s (DetermineMaxWaitForFrame keeps them while the NACK history is the
  //    default 1000 ms: 3 x 1000 ms is not below kMaxWaitForFrame);
  //  - video_receive_stream_timeout_tracker.cc: the wait is the keyframe one
  //    until the first frame is released, then the frame one, and it re-arms
  //    for another wait after each firing (HandleTimeoutTask);
  //  - video_receive_stream2.cc OnDecodableFrameTimeout: no request when no
  //    packet came for kInactiveDuration (5 s) or while a keyframe packet
  //    arrived within max_wait_for_keyframe (IsReceivingKeyFrame).
  TimeDelta max_wait_for_keyframe = TimeDelta::Millis(200);
  TimeDelta max_wait_for_frame = TimeDelta::Seconds(3);
  TimeDelta stream_inactive_after = TimeDelta::Seconds(5);
  size_t max_tracked_frames = 512;
  EventSink* events = nullptr;
};

struct KeyframeRequestStats {
  uint64_t frames_received = 0;
  uint64_t frames_decodable = 0;
  uint64_t frames_dropped = 0;      // Undecodable, discarded at the next keyframe.
  uint64_t pli_sent = 0;
  uint64_t fir_sent = 0;
  uint64_t lntf_sent = 0;
  Histogram time_to_keyframe_ms;    // First request -> keyframe received.
};

class KeyframeRequester : public MetricsSource {
 public:
  explicit KeyframeRequester(KeyframeRequestConfig cfg = {});

  // A complete frame (all packets present) was assembled.
  void OnFrame(const FrameInfo& f, Timestamp now);
  // Packets of a frame are permanently lost (NACK gave up).
  void OnFrameLost(int64_t frame_id, Timestamp now);
  void OnDecoderError(Timestamp now);
  // A media packet arrived (`keyframe_packet`: the depacketizer marks it as
  // part of a keyframe). Feeds the decode time-out, which does not fire while a
  // keyframe is arriving or when the stream is idle. With `rtp_timestamp`, a
  // packet of the last keyframe's RTP timestamp counts as a keyframe packet
  // too (RtpVideoStreamReceiver2::UpdatePacketReceiveTimestamps, issue #335).
  void OnMediaPacket(Timestamp now, bool keyframe_packet, std::optional<uint32_t> rtp_timestamp = std::nullopt);
  // A trigger decided elsewhere (the NACK list overflowed). Merged
  // with the other triggers of the same Process(). `reason` is an event name.
  void OnExternalRequest(Timestamp now, const char* reason);
  // New receiver or stream switch: needs a FIR (full intra request).
  void OnStreamStart(Timestamp now);

  // Feedback to send now.
  std::vector<FeedbackMessage> Process(Timestamp now);
  // When Process must run next: at once for a pending request or loss notification, otherwise when the decode
  // time-out is due (MinusInfinity before the first Process).
  Timestamp NextProcessTime() const;
  // Frames that became decodable, in order. Safe to pass to the decoder.
  std::vector<int64_t> TakeDecodableFrames();
  // A frame left the frame scheduler for the decoder. The decode time-out runs from here,
  // as libwebrtc's does from VideoStreamBufferController::OnFrameReady (OnEncodedFrameReleased), not
  // from the frame becoming decodable: the scheduler's wait for the render time comes first.
  void OnFrameReleased(Timestamp now);

  bool waiting_for_keyframe() const { return request_pending_; }
  const KeyframeRequestStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::loss
```

```cpp
namespace sm::loss {

// RTCP packet types used by the library.
inline constexpr uint8_t kRtcpSr = 200;
inline constexpr uint8_t kRtcpRr = 201;
inline constexpr uint8_t kRtcpSdes = 202;
inline constexpr uint8_t kRtcpBye = 203;
inline constexpr uint8_t kRtcpXr = 207;  // Extended reports (RFC 3611).
inline constexpr uint8_t kRtcpRtpfb = 205;  // Transport-layer feedback (NACK, transport-cc).
inline constexpr uint8_t kRtcpPsfb = 206;   // Payload-specific feedback (PLI, FIR, LNTF, REMB).

// Generic NACK: lost RTP sequence numbers of one media SSRC.
struct Nack {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
  // In the order they were requested. Serialization packs each run of numbers
  // within 16 of the item's first number into one PID+BLP item.
  std::vector<uint16_t> seqs;
};

// Picture loss indication: the decoder lost reference pictures.
struct Pli {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
};

// Full intra request: one entry per requested SSRC. `seq_nr` increases by one
// for each new request and lets the sender ignore retransmitted requests.
struct FirEntry {
  uint32_t ssrc = 0;
  uint8_t seq_nr = 0;
};
struct Fir {
  uint32_t sender_ssrc = 0;
  std::vector<FirEntry> entries;
};

// Loss notification: tells the sender how far the receiver has decoded and
// received, so it can decide whether a keyframe is needed. Sequence numbers
// are those of the frames' generic sequence (16 bits, wrapping).
struct LossNotification {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
  uint16_t last_decoded = 0;
  uint16_t last_received = 0;  // Within 32767 after last_decoded (wrapping).
  // True when every frame that has been received since last_decoded can be
  // decoded once the missing ones arrive (no keyframe needed yet).
  bool decodability_flag = false;
};

// At most this many 32-bit words of NACK items fit one RTCP packet; further
// sequence numbers are dropped by SerializeNack (the session splits earlier).
inline constexpr size_t kMaxNackItems = 65535 - 3;

// Each Serialize returns an empty vector when the message cannot be encoded
// (a NACK with no sequence numbers, a FIR with no entries, a loss notification
// whose last_received is not within 32767 after last_decoded).
std::vector<uint8_t> SerializeNack(const Nack& n);
std::vector<uint8_t> SerializePli(const Pli& p);
std::vector<uint8_t> SerializeFir(const Fir& f);
std::vector<uint8_t> SerializeLossNotification(const LossNotification& l);

// Each Parse takes exactly one RTCP packet (header included) and returns
// nullopt for a wrong packet type or FMT, a bad version, a length that does
// not match the data, or an empty / truncated payload.
std::optional<Nack> ParseNack(std::span<const uint8_t> data);
std::optional<Pli> ParsePli(std::span<const uint8_t> data);
std::optional<Fir> ParseFir(std::span<const uint8_t> data);
std::optional<LossNotification> ParseLossNotification(std::span<const uint8_t> data);

// --- Compound RTCP -------------------------------------------------------------

enum class RtcpType {
  kSenderReport,
  kReceiverReport,
  kNack,
  kTransportCc,
  kPli,
  kFir,
  kLossNotification,
  kRemb,
  kSdes,
  kBye,
  kXr,
  kOther,  // Valid RTCP header, type the library does not interpret.
};

// One packet inside a compound RTCP datagram. `data` includes the header.
struct RtcpPacketView {
  uint8_t packet_type = 0;
  uint8_t fmt = 0;  // The count / FMT field of the first byte.
  RtcpType type = RtcpType::kOther;
  std::span<const uint8_t> data;
};

// Splits a compound RTCP datagram into its packets, validating each header
// (version 2, length inside the datagram, padding only on the last packet).
// Returns nullopt for an empty datagram, a bad header or trailing bytes.
std::optional<std::vector<RtcpPacketView>> SplitCompoundRtcp(std::span<const uint8_t> data);

// Concatenates packets into a compound datagram. As libwebrtc does, the first
// packet must be an SR or an RR (use an RR with no blocks if there is nothing
// to report), and only the last packet may carry the padding bit (RFC 3550
// 6.1); otherwise returns an empty vector. Reduced-size RTCP
// (RFC 5506) is sent without this wrapper.
std::vector<uint8_t> BuildCompoundRtcp(std::span<const std::vector<uint8_t>> packets);

}  // namespace sm::loss
```

## Verification notes

Pass threshold derived analytically: each unrecoverable loss costs libwebrtc's decode time-out (3 s from the last released frame) + RTT + keyframe transit, about 93 frames, so the longest freeze is 3.1 s and 2% frame loss leaves 28-49% of frames decodable on seeds 1-5 (3-10% without keyframe requests). The v1 repair window gave 83% and 0.5 s until #167 deleted it. [#335](../../fixes/335-keyframe-packets.md): a 1 fps keyframe that took 0.5 s to arrive was asked for again at 400 ms because only its first packet counted as a keyframe packet; with every packet counted, the 1 fps repro matches libwebrtc (no keyframe requests, mouth-to-ear p95 about 860 ms).
