# 3.7 NACK/FEC protection selection

Section 3, *Packet loss*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Picking a protection level -> loss-rate-driven trade-off between FEC and NACK, based on RTT

## The issue

NACK and FEC protect against loss in different regimes, and a fixed choice is wrong most of the time. NACK costs almost nothing when there is no loss but adds one round trip of delay per repair, which is useless when the RTT is long. FEC repairs instantly but always costs bandwidth, which wastes capacity on clean links and steals bitrate from the video itself.

The right mix depends on the current RTT, the loss rate and whether losses come in bursts, and all three change during a call (Wi-Fi to LTE, a congested hop). Choosing too little FEC leaves frames broken; choosing too much reduces quality and can even cause the congestion that creates the loss.

## Design

- Low RTT: retransmission arrives well inside the playout budget, so NACK

```
  alone repairs loss at near-zero overhead.
```

- High RTT: a retransmission would arrive too late; FEC must carry the

```
  protection.
```

- In between: hybrid. NACK stays on and FEC covers only part of the loss.

The FEC rate is chosen analytically: for a frame of k media packets the controller picks the smallest m parity packets such that the probability of more than m losses among k+m packets (binomial, filtered loss p) is below a residual-loss target. The target is strict (1%) at high RTT and relaxed toward NACK-only (10%) at low RTT. Overhead is capped. The result is ULPFEC's protection parameters (loss/ulpfec.h): the rate m/k in Q8, one frame per FEC block and random masks, which libwebrtc's FecControllerDefault always picks (fec_controller_default.cc:138-143).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#3-packet-loss) for the differences from libwebrtc. The FEC rate is the smallest parity count that brings the binomial frame-loss probability under a target that moves from 10% (low RTT, NACK still helps) to 1% (high RTT). This is an analytical replacement for libwebrtc's lookup tables. Its decision is ULPFEC's `FecProtectionParams`: the rate in Q8 (so that `NumFecPackets` gives back the parity count), one frame per block and random masks, which `FecControllerDefault` always picks (`fec_controller_default.cc:138-143`); the burst-length input that chose this library's interleaved masks is gone with them (#29).

## Implementation skeleton

Files: [include/sm/loss/protection_controller.h](../../../include/sm/loss/protection_controller.h), [src/loss/protection_controller.cc](../../../src/loss/protection_controller.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::loss {

struct ProtectionConfig {
  TimeDelta low_rtt = TimeDelta::Millis(30);    // <= : NACK only.
  TimeDelta high_rtt = TimeDelta::Millis(150);  // >= : FEC carries protection.
  double target_residual_fec_only = 0.01;
  double target_residual_hybrid = 0.10;
  double max_overhead = 0.5;       // Max parity / media packets.
  double min_loss_for_fec = 0.005;
  double loss_smoothing = 0.3;     // EMA weight of each new loss report.
  EventSink* events = nullptr;
};

struct ProtectionInput {
  TimeDelta rtt;
  double loss_rate = 0;            // Fraction lost since last report.
  double packets_per_frame = 5;
};

struct ProtectionDecision {
  bool nack = true;
  ulpfec::FecProtectionParams fec;  // fec_rate 0: no FEC.
  double filtered_loss = 0;
  double expected_residual = 0;    // Predicted frame loss after FEC.
};

// P(X > m), X ~ Binomial(n, p).
double BinomialTail(int n, int m, double p);

class ProtectionController : public MetricsSource {
 public:
  explicit ProtectionController(ProtectionConfig cfg = {}) : cfg_(cfg) {}
  ProtectionDecision Update(const ProtectionInput& in, Timestamp now = Timestamp::Micros(0));
  const ProtectionDecision& last() const { return last_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::loss
```

## Verification notes

No defects found. At low RTT the controller chooses NACK only (overhead equals the loss rate); at 300 ms RTT it reaches 98.8% on-time delivery at about 27% overhead. Video RED+ULPFEC is off beside NACK for H.264 and Generic, as libwebrtc's `ShouldDisableRedAndUlpfec` decides (`rtp::ShouldDisableRedAndUlpfec`, [fix record #7](../../fixes/7-no-fec-beside-nack.md)); the controller only runs where libwebrtc would protect (NACK off, or VP8/VP9).
