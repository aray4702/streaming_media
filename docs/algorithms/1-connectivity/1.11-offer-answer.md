# 1.11 Offer/answer generation

Section 1, *Connectivity*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Agreeing on codecs, extensions and transports -> JSEP offers and answers for Opus, H.264, RTX, transport-cc and the data section

## The issue

An offer lists what one side can do; the answer must pick from it: the codecs both support, in the offerer's order, with the offerer's payload types, with the right extensions and transport. Getting it wrong yields a call without audio or video, or a mismatch that only shows once media flows.

## Design













libwebrtc M157 counterpart: `pc/media_session.{h,cc}`, `pc/codec_vendor.{h,cc}`, `pc/payload_type_suggester`, `p2p/base/transport_description_factory.{h,cc}`. Differences from libwebrtc: [libwebrtc parity inventory](../../design/libwebrtc-parity.md), section [10.18](../../design/libwebrtc-parity.md#1018-offeranswer-generation-srcpcmedia_sessioncodec_vendorsdp_payload_type_suggestertransport_description_factorycc-c6-part-2-1063). Requirement C6 part 2.

// Payload type and RTP header extension id assignment (C6 part 2, #1063): libwebrtc M157's
// pc/sdp_payload_type_suggester.{h,cc} (compare/webrtc/reference/pc/), with the PayloadTypePicker,
// PayloadTypeRecorder and RtpHeaderExtensionPicker it uses (call/payload_type_picker.cc, not in reference/).
//
// The recorders are kept per BUNDLE group (under the group's first mid), or per mid for a section that is not
// bundled, with a local and a remote payload type map and one header extension map each. `Update` records what a
// description set as local or remote uses, and the bundle groups from it (committed on an answer, as BundleManager
// does).
//
// Differences from libwebrtc (call/payload_type_picker.cc is not in reference/, so these follow its behaviour as
// media_session_unittest.cc pins it):
// - A payload type for a new codec is, in order: the one the local recorder already has for a matching codec; the
//   remote one for it if it is free locally; the codec's own payload type (the media engine's: opus 111, H.264 96
//   with RTX 97) if it is free; then the first free one in 96..127, then 35..63. libwebrtc's picker keeps a table of
//   default assignments instead of the engine's payload type; for this library's codecs both give the same values.
// - A header extension id is the recorder's id for the URI, else the preferred id if no other URI has it, else the
//   highest free id from 14 down to 1, then (two-byte ids allowed) 15 up to 255. This reproduces libwebrtc's
//   offers (for example toffset at 14 and video-orientation at 13 next to the audio section's ids).
// - No BundlePolicy: bundle groups are taken from the descriptions.

namespace sm::pc {

enum class RtpTransceiverIdDomain { kOneByteOnly, kTwoByteAllowed };

  bool AddLocalMapping(std::string_view mid, int payload_type, const Codec& codec);
  // An id for `extension` on `mid`; nullopt when none is free in `id_domain`.

                                                 RtpTransceiverIdDomain id_domain);
  // Records `extension.id` as mapped to its URI.
  bool AddRtpHeaderExtensionMapping(std::string_view mid, const RtpExtension& extension, bool local);
  // Records the bundle groups and the payload types and header extensions of `description`, set as local or
  // remote with `type`. Payload types that it does not use are released. False on a payload type conflict.
  bool Update(const SessionDescription* description, bool local, p2p::SdpType type);

  };
  Recorder& LookupRecorder(std::string_view mid);

  bool IsPayloadTypeSeen(int payload_type) const { return seen_payload_types_.count(payload_type) > 0; }

  std::vector<ContentGroup> pending_bundle_groups_;  // From the last offer.

  std::set<int> seen_payload_types_;
  std::map<int, ExtensionKey> extension_ids_;  // Every id handed out or recorded, across all sections.
};

// Options for offer/answer generation (C6 part 2, #1063): libwebrtc M157's pc/media_options.h and

//
// Differences from libwebrtc: no codec preferences (`codec_preferences`, setCodecPreferences), no crypto options

namespace sm::pc {

inline constexpr char kDefaultRtcpCname[] = "DefaultRtcpCname";

inline bool RtpTransceiverDirectionHasSend(RtpTransceiverDirection d) {
  return d == RtpTransceiverDirection::kSendRecv || d == RtpTransceiverDirection::kSendOnly;
}
inline bool RtpTransceiverDirectionHasRecv(RtpTransceiverDirection d) {
  return d == RtpTransceiverDirection::kSendRecv || d == RtpTransceiverDirection::kRecvOnly;
}
inline RtpTransceiverDirection RtpTransceiverDirectionFromSendRecv(bool send, bool recv) {
  if (send && recv) return RtpTransceiverDirection::kSendRecv;
  if (send) return RtpTransceiverDirection::kSendOnly;
  if (recv) return RtpTransceiverDirection::kRecvOnly;
  return RtpTransceiverDirection::kInactive;
}
inline RtpTransceiverDirection RtpTransceiverDirectionReversed(RtpTransceiverDirection d) {
  switch (d) {
    case RtpTransceiverDirection::kSendOnly:
      return RtpTransceiverDirection::kRecvOnly;
    case RtpTransceiverDirection::kRecvOnly:
      return RtpTransceiverDirection::kSendOnly;
    default:
      return d;
  }
}

  bool bundle_enabled = false;

// rtc_base/unique_id_generator's UniqueRandomIdGenerator (C6 part 2, #1063): random non-zero 32-bit ids, never the
// same one twice (SSRCs for the m= sections). Not in compare/webrtc/reference/; it draws from
// sm::tls::CreateRandomNonZeroId as libwebrtc draws from its crypto random source.

namespace sm::pc {

class UniqueRandomIdGenerator {
 public:
  UniqueRandomIdGenerator() = default;
  explicit UniqueRandomIdGenerator(const std::vector<uint32_t>& known_ids) : known_ids_(known_ids.begin(), known_ids.end()) {}
  uint32_t GenerateId() {
    while (true) {
      auto pair = known_ids_.insert(tls::CreateRandomNonZeroId());
      if (pair.second) return *pair.first;
    }
  }
  bool AddKnownId(uint32_t value) { return known_ids_.insert(value).second; }

};
