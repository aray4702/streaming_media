# 1.10 SDP model and parse/write

Section 1, *Connectivity*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Describing a call to a peer, a browser included -> the session description model and SDP text in both directions

## The issue

Before a call, the peers describe it to each other in SDP: media sections, codecs, extensions, candidates, fingerprints and BUNDLE. Browsers speak this text format. We need the structure and exact parse and write rules, or a browser's offer is rejected or misread.

## Design

The session description model (#1062, C6 part 1): libwebrtc M157's pc/session_description.{h,cc} (compare/webrtc/reference/pc/). A SessionDescription is what an SDP offer or answer says: its contents (one per m= section: a mid, a protocol type, rejected/bundle-only, and a media description), its transports (ICE and DTLS per mid, sm/p2p/transport_description.h), its groups (BUNDLE) and the session-level msid signalling, extmap-allow-mixed and cryptex. webrtc_sdp (sm/pc/webrtc_sdp.h) writes and reads it; offer/answer generation (C6 part 2) builds it.

Differences from libwebrtc: the deprecated ExtmapAllowMixed enum is left out, and the payload types are ints (sm/pc/codec.h).

SDP parse and write (#1062, C6 part 1): libwebrtc M157's api/webrtc_sdp.{h,cc} (compare/webrtc/reference/api/). SdpSerialize writes a session description (with its candidates) as libwebrtc writes it, line for line; SdpDeserialize reads one with libwebrtc's rules: the same accepted syntax, the same lines kept and ignored, and the same SdpParseError (the failing line and libwebrtc's reason) when it fails.

RFC 4566 (SDP), RFC 8839 (ICE), RFC 5888 / RFC 8843 (groups, BUNDLE), RFC 8122 / RFC 4145 (fingerprint, setup), RFC 8285 (extmap), RFC 5576 (ssrc, ssrc-group), RFC 8830 (msid), RFC 8851/8853 (rid, simulcast), draft-ietf-mmusic-sctp-sdp (sctp-port, max-message-size).

Differences from libwebrtc (also in docs/design/libwebrtc-parity.md, section 10.x): - A candidate's TLS fingerprint extension is checked but not kept. A candidate with a hostname (mDNS) address, and a c= line with a hostname, are kept with the name as their address (SetIP), as libwebrtc keeps them (#1152); the ICE agent resolves the name (sm/p2p/p2p_transport_channel.h). - No UMA histograms (WebRTC.PeerConnection.SdpBandwidth) and no logging of ignored lines. - A track id or a track without one gets 8 random characters from sm::tls::CreateRandomString, as libwebrtc's

```
  CreateRandomString.
```

JSEP's session description and ICE candidate objects (#1062, C6 part 1): libwebrtc M157's api/jsep.h, api/jsep_ice_candidate.cc (compare/webrtc/reference/api/) and the SessionDescriptionInterface implementation (api/jsep_session_description.cc / pc/jsep_session_description.cc, not in compare/webrtc/reference/; this follows M157's behaviour): a SessionDescription with its type (offer, pranswer, answer, rollback), session id and version, and the ICE candidates of each m= section, which also set that section's default address (c= and the m= port).

Differences from libwebrtc: no observers (CreateSessionDescriptionObserver, SetSessionDescriptionObserver) and no sequence checker, since the library starts no threads.

A codec as SDP describes it (#1062, C6 part 1): libwebrtc M157's media/base/codec.{h,cc} (FeedbackParam, FeedbackParams, Codec) and the constants of media/base/media_constants.{h,cc} the SDP layer uses (compare/webrtc/reference/media/base/; media_constants.h is not there, so the values are its M157 ones).

Differences from libwebrtc: - The payload type is an int (-1 = not set, as Codec::kIdNotSet), not the PayloadType class. - No SdpAudioFormat/SdpVideoFormat constructors, no scalability modes, no codec matching (Matches,

```
  MatchesRtpCodec, FindMatchingVideoCodec, the H.264 profile helpers) and no AddDefaultFeedbackParams: offer/answer
  generation (C6 part 2) brings them with media/base/codec_comparators.
```

The streams an m= section sends (#1062, C6 part 1): libwebrtc M157's media/base/stream_params.{h,cc} (SsrcGroup, StreamParams, the stream lookups) and media/base/rid_description.{h,cc} (compare/webrtc/reference/media/base/).

Difference from libwebrtc: GenerateSsrcs takes the id generator as a function (UniqueRandomIdGenerator comes with offer generation, C6 part 2).

a=simulcast and a=rid (#1062, C6 part 1): libwebrtc M157's pc/simulcast_description.{h,cc} and pc/simulcast_sdp_serializer.{h,cc} (compare/webrtc/reference/pc/; simulcast_description.h is not there, so the declarations follow the .cc and M157's header).

Difference from libwebrtc: SerializeRidDescription matches a RID's codecs to the m= section's by name (case-insensitive), clock rate, channels and fmtp parameters, with the SDP defaults filled in (VP9 profile-id, H.264 packetization-mode, AV1 profile, H.265 tx-mode) and the level ones left out (profile-level-id, level-id, level-idx, tier), standing in for IsSameRtpCodecIgnoringLevel (media/base/codec_comparators, C6 part 2).

The m= line's <proto> (#1062, C6 part 1): libwebrtc M157's pc/media_protocol_names.{h,cc} (compare/webrtc/reference/pc/).

The parts of libwebrtc M157's api/media_types.h, api/rtp_transceiver_direction.h, api/rtp_parameters.h (RtpExtension, RtcpFeedbackType) and api/rtp_header_extension_id.h that the session description model uses (#1062, C6 part 1). api/rtp_parameters.h and api/rtp_transceiver_direction.h are not in compare/webrtc/reference/; the types follow their M157 declarations.

libwebrtc M157 counterpart: `api/jsep.h`, `api/jsep_session_description`, `pc/session_description.{h,cc}`, `pc/webrtc_sdp.{h,cc}`, `media/base/codec.{h,cc}`, `media/base/stream_params.{h,cc}`, `api/rtp_parameters.h`, `pc/media_protocol_names.{h,cc}`. Differences from libwebrtc: [libwebrtc parity inventory](../../design/libwebrtc-parity.md), section [10.16](../../design/libwebrtc-parity.md#1016-session-description-model-and-sdp-parsewrite-srcpcwebrtc_sdpsession_descriptionjsepcodecstream_paramssimulcast_descriptionmedia_protocol_namescc-c6-part-1-1062). Requirement C6 part 1. A hostname (mDNS) candidate, and a `c=` line or `raddr` with a hostname, are kept with the name as the address, as libwebrtc's `SetIP` keeps it (#1152); the ICE agent resolves the name (1.6).

        content.media_description()->set_cryptex_level(level);
      }
    }
  }
