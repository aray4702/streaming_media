# 6.11 Sample-rate conversion

Section 6, *Audio quality (APM)*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Device sample-rate mismatch -> resampler

## The issue

Audio hardware runs at whatever rate the device prefers: 44.1 kHz on many Macs and USB devices, 48 kHz on most phones, 16 kHz on some embedded codecs and Bluetooth headsets. Processing runs at 16 or 48 kHz, and codecs at their own rates. Converting between rates is unavoidable.

Crude conversion (dropping samples or linear interpolation) folds high frequencies back into the audible band (aliasing) and dulls the sound. Conversion between rates that are not simple multiples, like 44.1 kHz and 48 kHz, needs fractional-ratio resampling that keeps exact sample counts over time.

## Design

rate). Polyphase windowed-sinc (Kaiser) resampler for any rational ratio in_rate:out_rate (8k, 16k, 22.05k, 32k, 44.1k, 48k...). The anti-aliasing cutoff sits at 0.92 x the lower Nyquist frequency; `taps_per_phase` trades quality for CPU and is multiplied by the decimation factor when down-sampling so the transition band stays narrow relative to the output Nyquist. Streaming: state is kept across calls, any input block size is accepted.

The Audio Device Module (platform audio I/O, device switching) is platform glue rather than an algorithm and is out of scope; the resampler is what bridges device and processing rates.

Public API (generated from the header; private members omitted):

```cpp
namespace sm::audio {

class Resampler : public MetricsSource {
 public:
  Resampler(int in_rate, int out_rate, int taps_per_phase = 32, double kaiser_beta = 8.0);
  // Appends resampled output to `out`.
  void Process(std::span<const float> in, std::vector<float>& out);
  int in_rate() const { return in_rate_; }
  int out_rate() const { return out_rate_; }
  // Group delay in output samples.
  double delay_out_samples() const;
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::audio
```

## Verification notes

Defect found: when decimating, the filter used too few taps (transition band several kHz wide), so a 10 kHz tone aliased at only -36 dB into 48 -> 16 kHz output. Taps now scale with the decimation factor: 91 dB rejection, 107 dB SNR.
