# 5.1 Transport-wide CC feedback (and REMB)

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Fine-grained per-packet feedback -> transport-cc (Transport-Wide CC) RTCP feedback
- Receiver-side bandwidth hints -> REMB (legacy)

## The issue

A congestion controller needs to know, for each packet, when it arrived, because queue build-up first shows as increasing delay well before any loss. Classic RTCP receiver reports give only averages once per second and are per media stream, so they are too coarse and too slow for delay-based control. Feedback is sent by the receiver many times per second, so it must encode hundreds of arrivals compactly. The sender must then match it with its own send times, for every stream sharing the connection.

## Design

(draft-holmer-rmcat-transport-wide-cc-extensions-01) and REMB.

Every outgoing packet carries a transport-wide sequence number. The receiver reports, per sequence number, whether it arrived and the arrival time (250 us resolution); the sender joins that with its send history to get per-packet (send time, receive time, size) results, which feed the delay-based and loss-based estimators. As libwebrtc's TransportFeedbackAdapter::ProcessTransportFeedback, each receive time's offset from the feedback's base time is rounded down to 1 ms first (#365).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. Status chunks use run-length coding for runs of 14 or more, otherwise 1-bit or 2-bit status vectors. Each arrival delta is rounded to the nearest 250 us tick, half away from zero, as rtcp::TransportFeedback::AddReceivedPacket does (#365; checked against libwebrtc's builder by sm_rtcp_interop). The builder is libwebrtc's TransportSequenceNumberFeedbackGenenerator: arrivals stay 500 ms, a reordered packet moves the window start back and is reported again, no gap older than 0x7FFE is reported, a message that cannot take another packet ends, and the interval follows 5% of the local send estimate (50-250 ms, 100 ms to start). Its v1 builder (each arrival once, fixed 50 ms) and the `tcc` switch were deleted in #167. The session sends the first periodic feedback after the generator's default 100 ms, and the interval from the local send estimate applies from then on: `Call::EnsureStarted` (call/call.cc) starts the task that runs `ReceiveSideCongestionController::MaybeProcess` before the Call hears its start rate, and `TransportSequenceNumberFeedbackGenenerator::Process` returns the delay to its next run (#217).

## Implementation skeleton

Public API (generated from the header; private members omitted):

```cpp
namespace sm::cc {

struct PacketResult {
  int64_t seq = 0;  // Unwrapped transport sequence number.
  Timestamp send_time;
  Timestamp receive_time = Timestamp::PlusInfinity();  // +inf = lost.
  DataSize size;
  int probe_cluster = -1;
  bool received() const { return receive_time.IsFinite(); }
};

struct TransportFeedback {
  uint32_t sender_ssrc = 0;
  uint32_t media_ssrc = 0;
  uint16_t base_seq = 0;
  uint8_t feedback_count = 0;
  int32_t reference_time = 0;  // Units of 64 ms (24-bit signed on the wire).
  struct Packet {
    uint16_t seq = 0;
    bool received = false;
    int64_t delta_ticks = 0;   // 250 us ticks from the previous received packet.
  };
  std::vector<Packet> packets;
  // Absolute arrival time of each received packet (derived).
  std::vector<std::pair<uint16_t, Timestamp>> ArrivalTimes() const;
};

std::vector<uint8_t> SerializeTransportFeedback(const TransportFeedback& fb);
std::optional<TransportFeedback> ParseTransportFeedback(std::span<const uint8_t> data);

// REMB (draft-alvestrand-rmcat-remb): receiver-estimated max bitrate.
std::vector<uint8_t> SerializeRemb(uint32_t sender_ssrc, DataRate bitrate, const std::vector<uint32_t>& ssrcs);
std::optional<std::pair<DataRate, std::vector<uint32_t>>> ParseRemb(std::span<const uint8_t> data);

struct FeedbackBuilderStats {
  uint64_t packets = 0;
  uint64_t feedbacks = 0;
  uint64_t re_reported = 0;  // packets reported again after a report (kBackWindow, reordering).
};

// libwebrtc modules/remote_bitrate_estimator/transport_sequence_number_feedback_generator.*
// (periodic reports only; the on-request form of transport-wide-cc-02 is not
// used): arrivals stay for kBackWindow, a reordered packet moves the window
// start back and is reported again, no gap older than 0x7FFE is reported, and
// the interval follows the local send estimate (`Interval()`).

// Receiver side: records arrivals and periodically builds feedback.
class TransportFeedbackBuilder : public MetricsSource {
 public:
  explicit TransportFeedbackBuilder(uint32_t sender_ssrc = 0, uint32_t media_ssrc = 0)
      : sender_ssrc_(sender_ssrc), media_ssrc_(media_ssrc) {}
  void OnPacket(uint16_t transport_seq, Timestamp arrival);
  // The local send estimate changed; feedback may use 5% of it
  // (OnSendBandwidthEstimateChanged). Until the first call the interval is 100 ms.
  void OnSendBandwidthEstimateChanged(DataRate estimate);
  // Time between periodic reports.
  TimeDelta Interval() const { return send_interval_; }
  // Feedback covering everything since the previous call (may be split
  // into several messages when deltas do not fit). Empty if nothing new.
  std::vector<TransportFeedback> Build();
  const FeedbackBuilderStats& stats() const { return stats_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

// Sender side: remembers what was sent and turns feedback into results.
// libwebrtc modules/congestion_controller/rtp/transport_feedback_adapter.* (#569
// part 2), for draft-holmer transport feedback on one network route:
// - the history keeps a packet for 60 s from when it was added
//   (kSendTimeHistoryWindow), pruned as packets are added; there is no count cap;
// - a packet reported received leaves the history, so a second report of it
//   fails the lookup; a packet reported lost stays, and a later report may still
//   say it arrived;
// - data in flight is the size of the packets above the highest transport
//   sequence number any feedback has named (last_ack_seq_num_), found or not:
//   a packet below it that no feedback reported (its feedback was lost) is no
//   longer in flight;
// - the send time handed to the estimators is in whole milliseconds, as
//   ProcessSentPacket reads it from rtc::SentPacket::send_time_ms, which the
//   transport fills with Timestamp::ms(), rounded to the nearest (#897); the
//   history is pruned by the creation time, the clock's;
// - receive times are on a local base: the first feedback's receive time, then
//   moved by each feedback's base-time delta (rounded down to 1 ms); each
//   packet's time since its feedback's base time is rounded down to 1 ms (#365).
class SendHistory : public MetricsSource {
 public:
  // AddPacket + ProcessSentPacket: the packet is added when the pacer sends it.
  void OnPacketSent(uint16_t transport_seq, Timestamp send_time, DataSize size, int probe_cluster = -1);
  // ProcessTransportFeedback: results in feedback order (transport sequence
  // order); unknown sequence numbers are skipped. Empty if the feedback names no
  // known packet, which libwebrtc does not pass on (it returns nullopt).
  std::vector<PacketResult> OnFeedback(const TransportFeedback& fb, Timestamp now);
  // GetOutstandingData.
  DataSize InFlight() const { return in_flight_; }
  void ExportMetrics(MetricsWriter& w) const override;

  };
  SeqNumUnwrapper<uint16_t> unwrapper_;
  std::map<int64_t, Sent> history_;
  DataSize in_flight_;
  // Sequence numbers are never negative; -1 is below every real one.
  int64_t last_ack_seq_num_ = -1;
  Timestamp current_offset_ = Timestamp::MinusInfinity();
  std::optional<uint32_t> last_base_ticks_;  // last_transport_feedback_base_time_, 24-bit 64 ms ticks.
  uint64_t lost_ = 0, acked_ = 0, failed_lookups_ = 0;
};

}  // namespace sm::cc
```

## Test methods

**Unit tests** (deterministic, no network):

- `TransportFeedback`: `WireRoundTripMixedChunks`, `BuilderAndHistoryJoin`, `LateArrivalAfterReportIsCounted`, `SplitsWhenDeltaOverflows`, `RembRoundTrip`

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_TransportFeedback`: `EveryPacketReportedOnceWithinQuantization`

7 500 packets over 5% loss with jitter (reordering); feedback every 50 ms serialized to the real wire format, parsed and joined with the send history. Each packet must be reported received once (a reordered packet first reported lost comes back received, as libwebrtc's generator re-reports it), with arrival-time error within the 250 us quantization of the wire, and each time since the feedback's base time handed to the estimators rounded down to 1 ms, on the adapter's local time base, as libwebrtc's TransportFeedbackAdapter (#365, #569).

## Verification notes

No defects found; maximum arrival-time error 249 us. Issue #217: the first feedback went out at 50 ms where libwebrtc's goes out at 100 ms, so the first probe estimate came from the first cluster alone (`issue_120_rtx_payload_padding` seed 1: 913 kbps at 65 ms, libwebrtc 1608 at 115 ms); unit test `Session.TransportFeedbackFirstReportWaitsTheDefaultInterval`. Issue #569 part 2: the send history ported as libwebrtc's TransportFeedbackAdapter (60 s window by creation time instead of an 8192-packet cap, in-flight data above the last acknowledged sequence number, the local receive-time base, no update for a feedback that finds no packet); unit tests `TransportFeedbackAdapter.*`; the scenario suite is unchanged, metric for metric. Issue #897: the send time in each result kept the pacer's microseconds, where libwebrtc's adapter takes rtc::SentPacket::send_time_ms (transport_feedback_adapter.cc:184), so its estimators see whole milliseconds; on `issue_150_gcc_v2_high_jitter_seed10` seed 10 the acked rate differed from libwebrtc's at 1280 ms (470925 vs 471029 bps, yardstick #915) and matches it with the port; unit test `TransportFeedbackAdapter.SendTimeIsWholeMilliseconds`. The milliseconds are the transport's Timestamp::ms(), rounded to the nearest (api/units/timestamp.h:56-58; sm_compare's transport passes now.ms(), webrtc_call.cc:996), not rounded down: with rounding down the acked rate still differed at 2530, 3330 and 4380 ms (497269/550081/496731 vs libwebrtc's 496773/549522/496232), and rounded to the nearest it matches there (#897); unit test `TransportFeedbackAdapter.SendTimeIsRoundedToTheNearestMillisecond`.
