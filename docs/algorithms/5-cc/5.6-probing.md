# 5.6 Bandwidth probing

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Probing for more bandwidth safely -> bandwidth probing (padding / RTX probe clusters)

## The issue

A delay-based controller only learns about capacity it is using: it raises the rate slowly (about 8% per second) and backs off at the first sign of queueing. Starting a call at 300 kbps on a 5 Mbps link therefore takes tens of seconds to reach good quality. When the application sends less than the estimate (a static screen share, a paused video), the estimate is never tested and can become stale in either direction.

Probing sends short bursts at a higher rate (with padding if there is no media) and measures how fast they arrive. A real probe result lets the estimate jump in one step. The probes must be short, and their results must reject measurements that are too sparse to trust.

## Design

libwebrtc's ProbeController (ProbeControllerV2 below) decides when to probe: at start-up (clusters at 3x and 6x the start rate), again whenever an estimate reaches 70% of the last probe rate (exponential probing upward), when the max bitrate is raised, after a large drop, and periodically in ALR when the stream asks for it. ProbeBitrateEstimator turns the feedback of one probe cluster into a rate: 95% of the receive rate if the link could not keep up (receive < 90% of send), else the lower of the two.

Bitrate prober, `pacer v2`: libwebrtc's BitrateProber (pacing/bitrate_prober. {h,cc}, M157, compare/webrtc/reference/), with its defaults (WebRTC-Bwe-ProbingBehavior unset: max_probe_delay 10 ms, min_packet_size 200 B).

The prober holds the probe clusters GoogCC asked for and tells the pacer when the next probe burst is due. It becomes active when a media packet of at least min(RecommendedMinProbeSize, 200 B) is enqueued, so a probe never starts on a tiny first packet; each burst carries `rate x min_probe_delta` bytes (>= 2 ms of the cluster rate); the next burst is due when the bytes sent so far would have been sent at the cluster rate; a burst more than max_probe_delay late drops the whole cluster; a cluster ends after min_probes packets and min_bytes bytes.

Application-limited-region detector, `cc v2`: libwebrtc's AlrDetector and IntervalBudget (goog_cc/alr_detector.{h,cc}, pacing/interval_budget.{h,cc}, M157, compare/webrtc/reference/), with the settings it runs with when no field trial is set.

A budget of `bandwidth_usage_ratio` x the estimate refills with the time between sent packets and is drained by the bytes sent. The sender is application limited when the budget is more than `start_budget_level_ratio` full, and stops being so when it falls under `stop_budget_level_ratio`. GoogCC uses the state to mark the acknowledged-rate estimate, to start periodic ALR probes and to allow a probe after a drop (RequestProbe).

The ratios are 0.80, 0.40 and -0.60, not AlrDetectorConfig's 0.65/0.80/0.50 (issue #152). AlrDetectorConfig first asks AlrExperimentSettings for WebRTC-ProbingScreenshareBwe, and alr_experiment.cc fills an empty group of that trial with kDefaultProbingScreenshareBweSettings, "1.0,2875,80,40,-60,3" ("now default-on with fixed settings"), so the experiment's 80/40/-60 percent replace the struct defaults in every call. The prebuilt M157 libwebrtc holds that string, and its live detector's budget (sm_compare's alr rows, PR #210) enters ALR at 0.40 and leaves it under -0.60 with a budget of 0.80 x the estimate. alr_experiment.cc is not in compare/webrtc/reference/ yet (#57).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. Probe clusters are sent by the pacer at the probe rate, using padding when there is no media; the estimator ignores clusters with too few packets or bytes. They are libwebrtc's code (#48; the library's own probe controller and estimator, `cc v1`, were deleted in #167): `ProbeControllerV2` (`ProbeController`: clusters at 3x and 6x the start rate, further probes at 2x a result above 0.7 of the last probe, probes when the max or max allocated bitrate rises, `RequestProbe` after a big drop within 5 s in or just after an ALR, periodic ALR probes when a stream requests them, none while the estimate is limited by delay increase or loss), `ProbeBitrateEstimator` (receive/send ratio over 2 rejected, clusters expire after 1 s, the newest estimate wins), `AlrDetector` and `BitrateProber` (in the pacer). `AlrDetector` runs with the settings libwebrtc's does without field trials (#152): a budget of 0.80 x the estimate, ALR above 0.40 and out of it under -0.60, `WebRTC-ProbingScreenshareBwe`'s default `1.0,2875,80,40,-60,3` (`alr_experiment.cc`), which replaces `AlrDetectorConfig`'s 0.65/0.80/0.50; sm_compare read it from libwebrtc's live budget (PR #210). The loss-based state and the RTT limit decide the bandwidth-limited cause (#12, `GetBandwidthLimitedCause`). Remaining differences: no `NetworkStateEstimate`. The `GoogCcNetworkController` glue (#61): `GetPacingRates` (2.5 x the target until the first feedback, 1.1 x after, unless the streams set a pacing factor; padding rate), `StreamsConfig::pacing_factor` (#187: `rtp::Session` sets 1.1 when it adds a video stream with transport-cc, as `VideoSendStreamImpl`'s `GetConfiguredPacingFactor` does, so a video call paces at 1.1 x from the start), the packet-overhead rate off the video allocation (`RtpVideoSender::OnBitrateUpdated`) and the congestion-window frame drop against the video target. With libwebrtc's default `CongestionWindowConfig` the window never reaches the pacer (`SetCongested` stays false), as in libwebrtc. Call start as libwebrtc's (#62): `rtp::Session` asks for periodic ALR probes when it adds an audio stream with transport-cc, as `AudioSendStream::ConfigureStream` does unless `WebRTC-Audio-AlrProbing` is disabled (`audio_send_stream.cc:158-159, 297-308`), and turns them off again when it then adds a video stream with transport-cc, as `VideoSendStreamImpl`'s constructor does with `RateControlSettings::UseAlrProbing()` (off without field trials; `video_send_stream_impl.cc:487-523`), so an audio-only call probes every 5 s in ALR and a call with video does not (#355: the ALR state and probe clusters of both stacks are in the bwe trace of yardstick #359; libwebrtc's only probes after the start are `RequestProbe`s); the streams' `max_total_allocated_bitrate` reaches `ProbeController` after the initial probes, because libwebrtc creates GoogCC when the network comes up, before the streams start (`rtp_transport_controller_send.cc:413-428, 747-773`), so an audio-only call's 3x and 6x probes are not capped at twice the audio allocation; and `BitrateProber` waits for a 200-byte RTP packet without the transport overhead (`PacingController::SetTransportOverhead`; `pacing_controller.cc:234`).

namespace sm::cc {

struct ProbeCluster {
  int id = 0;
  DataRate rate;
  int min_probes = 5;
  DataSize min_bytes;
  // ProbeClusterConfig: when the cluster was requested and the
  // smallest time between two bursts (BitrateProber::RecommendedMinProbeSize).
  Timestamp at_time;
  TimeDelta min_probe_delta = TimeDelta::Millis(2);
};

// libwebrtc's ProbeController (goog_cc/probe_controller.{h,cc}, M157,
// compare/webrtc/reference/) with its defaults (WebRTC-Bwe-ProbingConfiguration
// unset) and no NetworkStateEstimate (the default GoogCC has no estimator):
//   - exponential probing when the network is available and the bitrates are
//     set: clusters at 3x and 6x the start rate, then 2x the result for as long
//     as it exceeds 0.7 of the last probe rate;
//   - a probe when the max bitrate or the max total allocated bitrate rises;
//   - after a big drop, one probe at 0.85 x the rate before it when the delay
//     detector recovers from overuse (RequestProbe), within 5 s of the drop and
//     in or just after an ALR;
//   - periodic ALR probing at 2x the estimate every 5 s, only when the stream
//     requests it (EnablePeriodicAlrProbing; off by default);
//   - no probes while the estimate is limited by delay increase, loss or RTT.
// A cluster has 5 packets and 15 ms of the probe rate, bursts 2 ms apart.
enum class BandwidthLimitedCause : int {
  kLossLimitedBweIncreasing = 0,
  kLossLimitedBwe = 1,
  kDelayBasedLimited = 2,
  kDelayBasedLimitedDelayIncreased = 3,
  kRttBasedBackOffHighRtt = 4,
};

struct ProbeControllerV2Config {
  double first_exponential_probe_scale = 3.0;
  double second_exponential_probe_scale = 6.0;
  double further_exponential_probe_scale = 2.0;
  double further_probe_threshold = 0.7;
  bool abort_further_probe_if_max_lower_than_current = false;
  TimeDelta repeated_initial_probing_time_period = TimeDelta::Seconds(5);
  TimeDelta initial_probe_duration = TimeDelta::Millis(100);
  TimeDelta initial_min_probe_delta = TimeDelta::Millis(20);
  TimeDelta alr_probing_interval = TimeDelta::Seconds(5);
  double alr_probe_scale = 2.0;
  bool probe_on_max_allocated_bitrate_change = true;
  bool probe_on_max_allocated_bitrate_change_without_alr = true;
  double first_allocation_probe_scale = 1.0;
  double second_allocation_probe_scale = 2.0;
  double allocation_probe_limit_by_current_scale = 2.0;
  int min_probe_packets_sent = 5;
  TimeDelta min_probe_duration = TimeDelta::Millis(15);
  TimeDelta min_probe_delta = TimeDelta::Millis(2);
  double loss_limited_probe_scale = 1.5;
  EventSink* events = nullptr;
};

class ProbeBitrateEstimator : public MetricsSource {

  };
  void EraseOldClusters(Timestamp timestamp);

## Verification notes

No defects found. Ramp-up takes 0.2 s with probing; without it, 80% is not reached within 30 s. Found in #62 from the `audio_only_lossy` traces on `parity-data`: libwebrtc's first probe goes out at 3990 ms, with the first audio packet of 200 RTP bytes, and its estimate stays at 300 kbps, while the library probed at 104 kbps at 10 ms and fell to 75-100 kbps. Over seeds 1-10 the target goes 140 -> 209 kbps (libwebrtc 212), padding 30 -> 62 kbps (61) and the queue maximum 6 -> 58 ms (45); `issue_62_audio_only_probing` locks it in.
