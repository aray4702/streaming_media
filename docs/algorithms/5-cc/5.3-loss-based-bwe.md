# 5.3 Loss-based bandwidth estimation

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Unknown or changing available bandwidth -> GCC: loss-based estimation

## The issue

Delay is not the only congestion signal. Some links drop packets without first building a queue: shallow buffers, policers, wireless links with random loss. Others have so much competing traffic that queue delay never stabilizes. If the sender ignores loss, it can keep sending into a link that discards a large share of its packets.

Not every loss means congestion, though: wireless links lose packets randomly at any rate. A controller that backs off on every loss starves itself on a lossy-but-fast link. It must distinguish light loss (ignore), moderate loss (hold) and heavy loss (back off), using enough packets that the measured loss rate means something.

## Design

Applied to the current target rate A once per measurement window:

```
  loss < 2%   no loss-based limit (the delay-based estimate governs)
  2% - 10%    hold: limit = A
  loss > 10%  decrease: limit = A * (1 - 0.5 * loss), at most once per
              300 ms + RTT
```

Loss is measured over windows of at least 1 s and 20 packets, so a lucky or unlucky handful of packets cannot swing the estimate. (libwebrtc v1 additionally caps increases at 8%/s after start-up; here the delay-based controller and probing own the upward direction.)

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. Deviation from libwebrtc v1: below 2% loss this controller does not limit at all (delay-based and probing own the upward direction), whereas libwebrtc caps increases at 8%/s after start-up.

## Implementation skeleton

Files: [include/sm/cc/loss_based_bwe.h](../../../include/sm/cc/loss_based_bwe.h), [src/cc/loss_based_bwe.cc](../../../src/cc/loss_based_bwe.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::cc {

struct LossBweConfig {
  double low_loss = 0.02;
  double high_loss = 0.10;
  TimeDelta decrease_interval = TimeDelta::Millis(300);
  TimeDelta min_window = TimeDelta::Seconds(1);
  int min_packets = 20;
  DataRate min_rate = DataRate::KilobitsPerSec(30);
  DataRate max_rate = DataRate::KilobitsPerSec(20000);
  EventSink* events = nullptr;
};

class LossBasedBwe : public MetricsSource {
 public:
  explicit LossBasedBwe(LossBweConfig cfg = {}) : cfg_(cfg), rate_(cfg.max_rate) {}
  void Reset() { rate_ = cfg_.max_rate; lost_ = total_ = 0; window_start_ = Timestamp::MinusInfinity(); }
  void SetRtt(TimeDelta rtt) { rtt_ = rtt; }
  // Accumulates results; returns the loss-based limit (max_rate = no limit).
  DataRate OnPacketResults(const std::vector<PacketResult>& results, DataRate current_target, Timestamp now);
  DataRate estimate() const { return rate_; }
  bool limiting() const { return rate_ < cfg_.max_rate; }
  double last_loss() const { return last_loss_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::cc
```

## Verification notes

Defect found: loss was measured over 20-packet intervals, and a lucky interval with no loss (about 4% likely at 15% loss) let the estimate jump from 153 to 2 338 kbps. Now loss windows are at least 1 s and decisions are applied to the current target.
