# 5.8 Encoder overshoot control (frame dropper)

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Encoder bitrate overshoot -> encoder rate control, frame dropper

## The issue

Encoders do not hit their target bitrate exactly. Scene changes, keyframes and complex content overshoot, and some hardware encoders run persistently 20-50% over target. The congestion controller then sees more traffic than it allowed, queues build, and the controller lowers the target, which the encoder overshoots again. Real bandwidth is wasted on the overshoot while video quality is cut. Something must enforce the budget by skipping frames when the encoder has spent too much, and correct the encoder's systematic error, without reacting to the single large keyframe every encoder legitimately produces.

## Design

Real encoders miss their target: scene changes and keyframes overshoot, and some hardware encoders run persistently hot. Two complementary tools:

FrameDropper: a port of libwebrtc's modules/video_coding/utility/frame_dropper.{h,cc} (M157), with its constants and defaults. A leaky bucket (the accumulator, in kbits) is filled by every encoded frame and leaks target/fps per captured frame. Above half a second of the target rate it raises a smoothed drop ratio (ExpFilter) and DropFrame() spreads the drops over time, at most 4 s of frames in a row. Keyframes and unusually large delta frames (> 3x the running average) are not added at once but spread over 0.5 s of frames. The accumulator is capped at 3 s of the target rate, and rescaled by new/old target when the target drops (SetRates). The caller order per captured frame is as VideoStreamEncoder: Leak(fps), then DropFrame(); SetRates() on a rate update; Fill() after each encoded frame. Keyframes are not exempt, as in libwebrtc.

The encoder's overshoot correction (EncoderOvershootDetector and EncoderBitrateAdjuster) is in encoder_bitrate_adjuster.h.

Encoder overshoot control (issue #5, stage 1).

EncoderOvershootDetector and EncoderBitrateAdjuster are ports of libwebrtc's video/encoder_overshoot_detector.{h,cc} and video/encoder_bitrate_adjuster.{h,cc} (M157, compare/webrtc/reference/), with their constants. VideoStreamEncoder runs the adjuster by default (RateControlSettings: bitrate_adjuster = true, adjuster_use_headroom = true): the encoder is configured with a bitrate lowered by how much it overshoots, so that its frames can be paced out at the target without building a queue; spare link headroom (the link allocation above the encoder target) pays for part of the overshoot.

The detector is the whole of libwebrtc's, one instance. The adjuster is libwebrtc's for one stream with one temporal layer, which is all this library sends (one-to-one calls, no simulcast or SVC): the per-layer arrays, the weighted average over temporal layers and the layout bookkeeping reduce to one detector that exists while the target and the frame rate are both positive.

```
   (rtc_base/rate_utilization_tracker.*, "newfangled headroom adjustment",
   on by default). That file is not in compare/webrtc/reference/ (reported on
   #57). Until it is, the factor comes from the detector's own

   newfangled adjustment is disabled.
```

- Rates are re-adjusted per captured frame, libwebrtc does it on every

```
   bitrate update (about every 25 ms to 1 s).
```

Takes `now`, reads no clock.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. FrameDropper is a port of libwebrtc's modules/video_coding/utility/frame_dropper.cc (M157) with its constants: 0.5 s leaky bucket, accumulator cap 3 s, drop-ratio, key-frame-ratio and frame-size ExpFilters, keyframes and delta frames over 3x the average spread over 0.5 s of frames, at most 4 s of frames dropped in a row, and the accumulator rescaled by new/old target when the target drops. Keyframes are not exempt, as in VideoStreamEncoder::OnFrame. The session layer's rtp::VideoSendController (issue #37, docs/design/send-controller.md) drives it per captured frame (Leak, DropFrame, SetRates, Fill). The input frame rate is measured as FrameCadenceAdapter does (RateStatistics over 2970 ms, VideoStreamEncoder::GetInputFramerateFps; the configured maximum while it is unavailable); RateStatistics (rtc_base/rate_statistics) and ExpFilter (rtc_base/numerics/exp_filter) are checked against the sources now in compare/webrtc/reference. The encoder's overshoot correction is a port of libwebrtc's video/encoder_overshoot_detector.cc and encoder_bitrate_adjuster.cc (cc/encoder_bitrate_adjuster.h; issue #5): the encoder is configured with the target lowered by the measured overshoot. It runs in VideoSendController and is on by default as in M157 (RateControlSettings bitrate_adjuster = true, adjuster_use_headroom = true; `bitrate_adjuster off` in a scenario). The link allocation is VideoSendStreamImpl::OnBitrateUpdated's (issue #326, `link_headroom on|off`, on): the encoder target less the protection, taken before the target is capped at the encoder maximum, so a video allocation above the maximum gives the adjuster headroom; below the maximum it equals the encoder target. Remaining differences (issue #5): the media utilization factor comes from the detector, not RateUtilizationTracker (rtc_base/rate_utilization_tracker); one stream with one temporal layer; rates adjusted per captured frame, not per bitrate update. The VideoStreamEncoder has no keyframe budget of its own: a keyframe request only sets next_frame_types_ (sticky until a keyframe is encoded, as here) and the keyframe then goes through the frame dropper like any frame.

```cpp
namespace sm::cc {

// rtc_base/numerics/exp_filter.{h,cc}: filtered = a^exp * filtered + (1 - a^exp) * sample,
// seeded by the first sample, optionally capped at `max`. Not in
// compare/webrtc/reference (reported on #57); written from the upstream class.
class ExpFilter {
 public:
  static constexpr float kValueUndefined = -1.0f;
  explicit ExpFilter(float alpha, float max = kValueUndefined) : alpha_(alpha), max_(max) {}
  void Reset(float alpha) {
    alpha_ = alpha;
    filtered_ = kValueUndefined;
  }
  float Apply(float exp, float sample) {
    if (filtered_ == kValueUndefined) {
      filtered_ = sample;
    } else if (exp == 1.0f) {
      filtered_ = alpha_ * filtered_ + (1 - alpha_) * sample;
    } else {
      const float alpha = std::pow(alpha_, exp);
      filtered_ = alpha * filtered_ + (1 - alpha) * sample;
    }
    if (max_ != kValueUndefined && filtered_ > max_) filtered_ = max_;
    return filtered_;
  }
  void UpdateBase(float alpha) { alpha_ = alpha; }
  float filtered() const { return filtered_; }

};

class FrameDropper : public MetricsSource {
 public:
  FrameDropper();
  // Back to the initial state (target 300 kbps, 30 fps).
  void Reset();
  // The caller's per-frame sequence, as VideoStreamEncoder::OnFrame:
  // Leak(fps) then DropFrame(). Returns true if the frame is to be dropped.
  bool ShouldDrop(double input_fps);
  void Leak(uint32_t input_framerate);
  bool DropFrame();
  // `target` is rounded to whole kbps as VideoStreamEncoder::OnBitrateUpdated does.
  void SetRates(DataRate target, double fps);
  // After encoding.
  void OnEncodedFrame(DataSize size, bool keyframe);
  double bucket_bytes() const { return accumulator_ * 1000.0 / 8.0; }
  double incoming_frame_rate() const { return incoming_frame_rate_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::cc
```

## Verification notes

Issue #53 ([fix record](../../fixes/53-cwnd-pushback.md)): keyframe bytes entered an uncapped bucket and a run of keyframe requests made the dropper drop every delta frame for seconds. Issue #5 ([fix record](../../fixes/5-frame-dropper-port.md)): replaced by the libwebrtc port (3 s cap, rescale on a rate drop); the 1.5 s cap and the keyframe exemption are gone. Issue #326: the link allocation was the capped encoder target, so above the 2.5 Mbps maximum the adjuster had no headroom and gave the encoder 2266-2270 kbps where libwebrtc gives 2404-2466 (issue_326_congestive_sync seeds 3 and 5, t = 3 s, parity-data-pr/pr/327); the protection returned to the allocator also came from the capped target. Both now follow rtp_video_sender.cc:885-939 and video_send_stream_impl.cc:902-914.
