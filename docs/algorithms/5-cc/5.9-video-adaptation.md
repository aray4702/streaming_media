# 5.9 Resolution/frame-rate adaptation and CPU overuse detection

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Low bandwidth -> adaptive resolution / framerate degradation (degradationPreference)
- CPU too slow to encode -> CPU overuse detector, which lowers resolution or fps

## The issue

When bandwidth falls, sending 720p at 30 fps with too few bits gives a blocky, unreadable picture. It is better to send fewer pixels or fewer frames at an adequate quality. Which to sacrifice depends on the content: a sports or camera feed should keep its frame rate, a slide deck should keep its resolution. The device's CPU can be the limit too: a phone or wearable that cannot encode 720p in real time drops frames, heats up and drains the battery regardless of the network.

Without adaptation, quality collapses under constraint. With naive adaptation, the format oscillates around a threshold, visibly switching resolution every few seconds.

## Design

DegradationController picks the encoded resolution and frame rate for a target bitrate using a bits-per-pixel budget:

```
  bitrate >= width * height * fps * bpp
```

Candidate formats are ordered by preference:

```
  maintain-framerate:  lower resolution only
  maintain-resolution: lower frame rate only (down to min_fps)
  balanced:            frame rate down to balanced_fps first, then
                       resolution, then frame rate down to min_fps
```

Going down needs bpp_down, going back up needs the larger bpp_up, so the format does not oscillate around a threshold. Resource limits (CPU overuse, quality scaler) impose an extra cap on pixels or fps.

CpuOveruseDetector: encode usage = encode time / frame interval, exponentially filtered. Above 85% for consecutive checks -> overuse (adapt down); below 42% -> underuse (adapt up), with a back-off after an adapt-up that caused overuse, to avoid oscillating.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. The resolution ladder alternates 3/4 and 2/3 linear scale steps (as libwebrtc's VideoAdapter); bpp_down/bpp_up hysteresis is 0.04/0.06 bits per pixel.

## Implementation skeleton

Files: [include/sm/cc/video_adaptation.h](../../../include/sm/cc/video_adaptation.h), [src/cc/video_adaptation.cc](../../../src/cc/video_adaptation.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::cc {

enum class DegradationPreference { kMaintainFramerate, kMaintainResolution, kBalanced, kDisabled };

struct VideoFormat {
  int width = 0;
  int height = 0;
  double fps = 0;
  int64_t pixels() const { return int64_t{width} * height; }
  bool operator==(const VideoFormat& o) const = default;
};

struct DegradationConfig {
  VideoFormat input{1280, 720, 30};
  DegradationPreference preference = DegradationPreference::kBalanced;
  double bpp_down = 0.04;
  double bpp_up = 0.06;
  double min_fps = 5;
  double balanced_fps = 15;
  int min_pixels = 320 * 180;
  EventSink* events = nullptr;
};

class DegradationController : public MetricsSource {
 public:
  explicit DegradationController(DegradationConfig cfg = {});
  VideoFormat OnTargetBitrate(DataRate target, Timestamp now = Timestamp::Micros(0));
  // Resource-driven steps (CPU overuse, quality scaler). Each call moves
  // the resource cap one step along the preference ladder.
  void OnResourceOveruse();
  void OnResourceUnderuse();
  VideoFormat current() const { return current_; }
  const std::vector<VideoFormat>& ladder() const { return ladder_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

struct CpuOveruseConfig {
  double high_threshold = 0.85;
  double low_threshold = 0.42;
  TimeDelta check_interval = TimeDelta::Seconds(5);
  int consecutive_checks = 2;
  double smoothing = 0.1;  // EMA weight per frame.
};

class CpuOveruseDetector : public MetricsSource {
 public:
  enum class Signal { kNone, kOveruse, kUnderuse };
  explicit CpuOveruseDetector(CpuOveruseConfig cfg = {}) : cfg_(cfg) {}
  void OnFrameEncoded(TimeDelta encode_time, TimeDelta frame_interval);
  Signal Check(Timestamp now);
  double usage() const { return usage_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::cc
```

**Unit tests** (deterministic, no network):

- `VideoAdaptation`: `LaddersFollowPreference`, `BitrateDrivesFormatWithHysteresis`, `CpuOveruseSignalsAndResourceCap`

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_VideoAdaptation`: `ResolutionFollowsBandwidth`, `CpuOveruseConvergesToSustainableResolution`

(a) Closed loop with capacity 3000 -> 400 -> 3000 kbps under maintain-framerate: the resolution must drop and recover. (b) A slow device (40 ms of encode per megapixel): the CPU detector must settle on a sustainable resolution without oscillating.
