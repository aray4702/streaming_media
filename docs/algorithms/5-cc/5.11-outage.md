# 5.11 Link outage detection and recovery

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Link outage, then recovery -> encoder pause, then keyframe on recovery; ICE restart if needed

## The issue

Links drop out entirely: a tunnel, an elevator, a Wi-Fi to LTE handover, a NAT rebinding. During the outage nothing comes back from the far end. A sender that keeps encoding fills its queues (and the network's) with media that will be seconds old when the link returns. Its bandwidth estimate is meaningless. The far end's decoder state is lost, so delta frames sent after recovery are undecodable. Recovery needs a deliberate sequence: pause, keep the connection alive, restart ICE if the path is gone, then resume with a keyframe and a cautious rate on what may now be a different path.

## Design

Watches feedback from the remote side (RTCP, transport feedback, any packet). States:

```
  kUp        feedback within degraded_after
  kDegraded  no feedback for degraded_after
  kDown      no feedback for down_after
```

Process() also proposes actions (OutageActions): an encoder pause on kDown, an ICE restart request after ice_restart_after of continuous outage, and on the first feedback after kDown a resume, a keyframe and a reset of the estimate to a fraction of the pre-outage rate.

libwebrtc M157 has no outage monitor and takes no sender action on an outage: SendSideBandwidthEstimation backs off on missing feedback (kMaxRtcpFeedbackInterval) and the receiver's decode time-out asks for the keyframe. So on the call path rtp::SendSideController runs Process() every time it processes, only to follow the link (state, metrics, events), and acts on none of these actions (issues #151, #849).

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. The monitor proposes an encoder pause, an ICE restart request, and on recovery a keyframe and an estimate reset to half the last good rate. libwebrtc has no outage monitor, so the `SendSideController` runs it only to follow the link (state, `sender.outage.*` metrics, `outage` events) and acts on none of them (issues #151, #849; only `cc v1` did, deleted in #167): the encoder keeps running, the congestion window drops frames, the pacer keeps sending, and the receiver's decode time-out asks for the keyframe once the link is back.

## Implementation skeleton

Files: [include/sm/cc/outage_monitor.h](../../../include/sm/cc/outage_monitor.h), [src/cc/outage_monitor.cc](../../../src/cc/outage_monitor.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::cc {

enum class LinkState { kUp, kDegraded, kDown };
const char* ToString(LinkState s);

struct OutageConfig {
  TimeDelta degraded_after = TimeDelta::Millis(600);
  TimeDelta down_after = TimeDelta::Millis(2000);
  TimeDelta ice_restart_after = TimeDelta::Seconds(5);
  double resume_rate_fraction = 0.5;
  EventSink* events = nullptr;
};

struct OutageActions {
  bool pause_encoder = false;
  bool resume_encoder = false;
  bool request_keyframe = false;
  bool ice_restart = false;
  bool reset_estimate = false;
  DataRate reset_rate;
};

class OutageMonitor : public MetricsSource {
 public:
  explicit OutageMonitor(OutageConfig cfg = {}) : cfg_(cfg) {}
  void OnFeedback(Timestamp now);
  void SetCurrentRate(DataRate r) {
    if (state_ == LinkState::kUp) last_good_rate_ = r;
  }
  OutageActions Process(Timestamp now);
  LinkState state() const { return state_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::cc
```

Explained difference (Owner, PR #184), owned by #24: on seeds 2 and 3 of `issue_151_outage_3s_v2` the receiver's decode-time-out PLI reaches the sender before the next capture, so that frame becomes the keyframe before the NACK arrives and the resends queue behind it (freeze 4666 / 3948 ms, repair 6.30 / 3.18 %; main 4067 / 4047 ms, 1.43 / 1.26 %; libwebrtc 3256 / 3175 ms, 0.36 / 0.53 %). libwebrtc's PLI lands after that capture because its frame release (FrameDecodeTiming) comes later; the other 8 of 10 seeds and the audio gap on all 10 match libwebrtc. Explained difference (Owner decision on issue #151, 2026-10-20): with every v2 switch on, `outage_3s` `cc.queue_p95_ms` stays above libwebrtc's (`issue_151_outage_3s_v2`, seeds 1-10 on main 0b45569: mean 64.2 vs 40.6 ms, sd 32.1 vs 4.0) while freeze total (3413 vs 3227 ms), repair (1.0 vs 0.4 %) and the longest audio gap (2980 vs 2977 ms) are in band. Every input to the recovery matches libwebrtc: in-flight accounting, overhead rate (#192), link-change timing (#190), the 300 ms keyframe-request interval (#195), no outage monitor and the tick order (#184), and `NackRequester::ClearUpTo` (#172). What remains is a phase race over which frame the congestion window drops first after `up`, which decides whether the NACK lands before, in or after the keyframe's tick; the mean swings with unrelated small inputs (50.5 -> 66.2 -> 64.2 ms across #198, #199 and #202). Seeds 2 and 3 stay tracked to #24, as above. Issue #849: nothing called `OutageMonitor::Process` on the call path, so its state stayed `up` and `sender.outage.outages` at 0 through every outage; `SendSideController::Process` now runs it and discards its actions (`SendSideController.OutageMonitorFollowsTheLinkAndTakesNoAction`). Every scenario's call metrics are unchanged; only the `outage` event counts appear.
