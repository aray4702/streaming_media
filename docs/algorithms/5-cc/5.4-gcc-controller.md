# 5.4 Send-side bandwidth estimation (GCC network controller)

Section 5, *Bandwidth, congestion and unstable links*, of [Problems WebRTC solves](../../02-webrtc-problems-solved.md). Problems addressed:

- Unknown or changing available bandwidth -> GCC (delay-based and loss-based estimation)

## The issue

Several estimates of the available bandwidth exist at once: delay-based, loss-based, the receiver's REMB hint and probe results. Each also has configured limits. The encoders need one target rate, and the pacer needs a rate to send at. Combining them incorrectly makes the system either ignore a real limit (overshooting into congestion) or let one stale estimate cap everything (stuck at low quality). The combination also has to be wired to the right inputs: transport feedback, RTT updates and periodic ticks.

## Design

Wires transport feedback into the delay-based estimator, the loss-based estimator, the acknowledged-bitrate estimator and the probe machinery, and produces the target rate for the encoders (min of delay-, loss- and REMB-based estimates, clamped to [min, max]) plus a pacing rate (target x pacing_factor) and any probe clusters to send.

See the [libwebrtc parity inventory](../../design/libwebrtc-parity.md#5-congestion-control) for the differences from libwebrtc. The target is min(delay-based, loss-based, REMB), clamped to [min, max]; the pacing rate is 2.5 x target. rtp::SendSideController adds congestion-window pushback (cc/congestion_window_pushback.h, a port of libwebrtc's CongestionWindowPushbackController with its drop-frame-only mode): when the data in flight exceeds target x (min feedback RTT + 350 ms) the encoder drops every N-th captured frame (SendRates::frame_drop_interval, SendSideController::DropCapturedFrame()). The pacing rate is not reduced. #166 ports goog_cc_network_control_unittest.cc against `GccController` with `cc v2` (`GoogCcNetworkController`, 9 cases): the 8 `GoogCcNetworkControllerTest` cases the API can express pass (`RespectsConfiguredPacingFactor` through `SetPacingFactor`, #187), `OnNetworkRouteChanged` in its first half (a route change without a starting rate has no counterpart: `ResetEstimate` always takes a rate, and keeps the configured min and max), `ProbeOnRouteChange` with the route's maximum configured up front, and `TriggersTargetRateUpdateWhenBandwidthLimitedChanges` on the `AlrDetector` state (only libwebrtc's RFC 8888 feedback generator reads `is_bandwidth_limited`). `GoogCcScenario.NoCrashOnVeryLateFeedback` is ported at the controller level. Not ported: `ProbeAfterRouteChangeWhenTransportWritable` (network availability belongs to the host stack's ICE), `LimitPacingFactorToUpperLinkCapacity` (a field trial, off in M157), and the other `GoogCcScenario` cases, which need libwebrtc's network emulation: the scenario suite and `sm_compare` cover their links (capacity steps, high loss, cross traffic, REMB caps), and the rest set field trials that are off by default (`WebRTC-CongestionWindow` sizes, `MaxRttLimit`, `SafeResetOnRouteChange`, `ResetOnAdapterIdChange`, `LossBasedControl`, `AddPacingToCongestionWindowPushback`) or send without transport-cc. **Default (#61):** a `rtp::Session` runs libwebrtc's components: `SessionConfig` and `SendSideConfig` default to `cc`, `pacer`, `allocator` and `packetization` v2, `VideoStreamConfig` to `keyframe` v2, and the test bench also to `audio` v2. v1 stays selectable per field (test bench `cc v1` etc.) until #167 deletes it; the component configs on their own (`GccConfig`, `PacerConfig`, `KeyframeRequestConfig`) keep version 1, so their unit tests test what they name. `tcc`, `rtcp` and `rtx` v1 are deleted (#167): transport-cc feedback, RTCP report timing and the RTX history are libwebrtc's only. `timing` and `neteq` v2 are not in this flip; they join when #24 and #62 finish. Approved deviation: the Opus frame-size model of `audio v2` (3.1, a model fitted to libwebrtc's trace, not libopus). Explained differences: `outage_3s` `cc.queue_p95_ms` under all v2 (5.11, #151) and `issue_53_cwnd_pushback` render fps, from the receive-side `FrameScheduler` drop rule (#24). Provisional locks (PR #180): `issue_151_outage_3s_v2` (3.1, tracked to #151) and `issue_76_tcc_v2_high_jitter` (4.6, tracked to #24). Provisional locks (PR #186, Owner 2026-10-20): `issue_53_cwnd_pushback` `video.render_fps >= 14` (was 22; libwebrtc 27.4, ours 16.0; tracked to #24, restored when `timing v2` joins the defaults) and `issue_120_rtx_payload_padding` `net.rtx_kbps >= 330` (was 380; libwebrtc 451, ours 344; tracked to #217; restored to 380 by #217's first-feedback timing, see 5.1).

## Implementation skeleton

Files: [include/sm/cc/send_side_bwe.h](../../../include/sm/cc/send_side_bwe.h), [src/cc/send_side_bwe.cc](../../../src/cc/send_side_bwe.cc).

Public API (generated from the header; private members omitted):

```cpp
namespace sm::cc {

// One row of the BWE trace (issue #149): what libwebrtc's RtcEventLog records as
// RtcEventBweUpdateDelayBased and RtcEventBweUpdateLossBased, plus the final
// target. sm_compare writes libwebrtc's rows in the same layout (BweTraceCsv in
// testbench/call.h), so tools/bwe_trace.py can lay the two stacks side by side.
// -1 marks a column the event does not have.
struct BweTraceRow {
  // kDetector: one TrendlineEstimator::Update with calculated deltas, i.e. one
  // completed send-time group (issue #152): detector = the state after it,
  // packets = the deltas seen so far (num_of_deltas_), and the trend columns below.
  // time_us is the feedback time. libwebrtc's rows come from its own
  // InterArrivalDelta and TrendlineEstimator fed with the feedback its GoogCC got.
  enum class Kind { kDelayBased, kLossBased, kTarget, kDetector };
  int64_t time_us = 0;
  Kind kind = Kind::kTarget;
  int64_t bitrate_bps = 0;
  int detector = -1;            // BandwidthUsage as an int (delay-based rows).
  int fraction_loss = -1;       // 0-255 (loss-based rows).
  int packets = -1;             // Packets in the loss report (loss-based rows).
  int loss_state = -1;          // LossBasedState (this library's loss-based rows only).
  int64_t loss_limit_bps = -1;  // LossBasedBweV2's loss-limited estimate (this library only).
  int64_t instant_ub_bps = -1;  // LossBasedBweV2's instant upper bound (this library only).
  // kDetector rows only (NaN elsewhere): the modified trend and the threshold after the
  // update, the group deltas it took, and the send and arrival time (ms) it was given.
  double modified_trend = std::numeric_limits<double>::quiet_NaN();
  double threshold = std::numeric_limits<double>::quiet_NaN();
  double send_delta_ms = std::numeric_limits<double>::quiet_NaN();
  double recv_delta_ms = std::numeric_limits<double>::quiet_NaN();
  double send_ms = std::numeric_limits<double>::quiet_NaN();
  double arrival_ms = std::numeric_limits<double>::quiet_NaN();
};

struct GccConfig {
  DataRate min_rate = DataRate::KilobitsPerSec(30);
  DataRate start_rate = DataRate::KilobitsPerSec(300);
  DataRate max_rate = DataRate::KilobitsPerSec(10000);
  double pacing_factor = 2.5;
  bool enable_probing = true;
  // 1: the original controller. 2 (`cc v2`): libwebrtc's GoogCC, ported in
  // stages (#61); so far the delay detector's front end (#19), the acked-rate
  // estimator and AimdRateControl (#15), and the AlrDetector, ProbeController
  // and ProbeBitrateEstimator (#48; the BitrateProber is in `pacer v2`), and
  // SendSideBandwidthEstimation with LossBasedBweV2 (#12), and GetPacingRates (#61).
  int version = 1;
  // `cc v2`: StreamsConfig::requests_alr_probing, which a screen-share stream
  // sets; periodic ALR probes are off otherwise.
  bool periodic_alr_probing = false;
  EventSink* events = nullptr;
  // `cc v2`: when set, rows are appended as libwebrtc's RtcEventLog would log them
  // (delay-based and loss-based updates when they change) and the target when it
  // changes. The test bench sets it for --link-trace.
  std::vector<BweTraceRow>* bwe_trace = nullptr;
};

struct NetworkControlUpdate {
  DataRate target_rate;
  DataRate pacing_rate;
  std::vector<ProbeCluster> probes;
  bool changed = false;
};

class GccController : public MetricsSource {
 public:
  explicit GccController(GccConfig cfg = {});
  NetworkControlUpdate Start(Timestamp now);
  void OnPacketSent(uint16_t transport_seq, Timestamp send_time, DataSize size, int probe_cluster = -1);
  NetworkControlUpdate OnTransportFeedback(const TransportFeedback& fb, Timestamp now);
  void OnRttUpdate(TimeDelta rtt);
  // The RTT the controller last took (rounded to whole ms with `cc v2`).
  TimeDelta last_rtt() const { return last_rtt_; }
  void OnRemb(DataRate remb);
  // `cc v2`: GoogCcNetworkController::OnTransportLossReport. The loss and packet
  // counts are the deltas between two receiver reports (summed over the report
  // blocks). Used for the loss rate until LossBasedBweV2 has three observations.
  NetworkControlUpdate OnTransportLossReport(int64_t packets_lost_delta, int64_t packets_delta, Timestamp now);
  // `cc v2`: StreamsConfig::max_total_allocated_bitrate, the sum of the maximum
  // bitrates the allocator hands out: a rise probes up to twice that rate, and
  // it caps every probe at twice that rate. Returns the clusters to send. No
  // effect with `cc v1`.
  std::vector<ProbeCluster> OnMaxTotalAllocatedBitrate(DataRate max_total_allocated_bitrate, Timestamp now);
  // The sum of the minimums the bitrate allocator must fund is a lower bound for
  // the estimates and the target (GoogCC use_min_allocatable_as_lower_bound_,
  // ClampConstraints). Never below the configured minimum.
  void SetMinAllocatable(DataRate r);
  // `cc v2`: StreamsConfig::min_total_allocated_bitrate and max_padding_rate,
  // which GetPacingRates() reads (the allocator's limits). Takes effect with the
  // next update.
  void SetPacingLimits(DataRate min_total_allocated, DataRate max_padding);
  // `cc v2`: StreamsConfig::pacing_factor (GoogCcNetworkController::OnStreamsConfig).
  // Once set, GetPacingRates() uses it in place of the defaults (2.5 before the
  // first transport feedback, 1.1 after it). A video stream with transport-cc sets
  // 1.1 from the start (VideoSendStreamImpl's kStrictPacingMultiplier, issue #187).
  // Takes effect with the next update.
  void SetPacingFactor(double factor);
  // `cc v2` with `pacer v2`: the pacing and padding rates as GetPacingRates() computes them (the
  // caller takes the minimum of the padding rate and the congestion-window pushback target).
  // `pacing_rate` of the update stays target x pacing_factor, for `pacer v1`.
  // GccConfig::pacing_factor is `pacer v1`'s; SetPacingFactor() sets this one.
  DataRate PacingRate() const;
  DataRate PaddingRate() const;
  // Periodic tick (e.g. every 25 ms): ALR probing and outage handling.
  NetworkControlUpdate OnProcessInterval(Timestamp now, DataRate current_send_rate);
  // Hard reset after a network route change / outage recovery.
  NetworkControlUpdate ResetEstimate(DataRate rate, Timestamp now);
  DataRate target() const { return target_; }
  // The lower bound in force (configured minimum, raised to the allocator's minimum).
  DataRate min_rate() const { return cfg_.min_rate; }
  // Largest (feedback time - send time) among the packets the last feedback
  // reported as received; nullopt if it reported none.
  std::optional<TimeDelta> last_feedback_max_rtt() const { return last_feedback_max_rtt_; }
  const DelayBasedBwe& delay_bwe() const { return delay_; }
  const AlrDetector& alr_detector() const { return alr_; }
  const ProbeControllerV2& probe_controller_v2() const { return probe2_; }
  const LossBasedBwe& loss_bwe() const { return loss_; }
  const SendSideBandwidthEstimation& send_side_bwe() const { return ssbe_; }
  const SendHistory& history() const { return history_; }
  void ExportMetrics(MetricsWriter& w) const override;

};

}  // namespace sm::cc
```

## Test methods

**Unit tests** (deterministic, no network):

- `SendSideBwe`: `StartProbesAndRembCap`
- `GoogCcNetworkController`: (not run)

**End-to-end test** (sender -> simulated network -> receiver, `tests/e2e/`):

- `E2E_SendSideBwe`: `CombinesDelayAndLossControllers`

A 1.5 Mbps link through three 20 s phases: clean, 5% loss (GCC 'hold' band) and 20% loss (decrease band). Each phase's target is compared with the previous one.
